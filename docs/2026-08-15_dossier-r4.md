# Dossier R4 — float fusion + extra intermediate precision (narrowed to per-op rounding, platform-scoped)

G3 register item 12. Inventory §R4 (register extension #9's platform
scoping); floats design `docs/2026-08-04_floats-design.md` §3.1;
module envelope statement FloatBits.lean:31–49. Proposal only —
batched for user ruling.

## 1. The latitude

An implementation may fuse floating-point operations (FMA, possibly
across statements) and may carry float32 intermediates at extra
precision, producing results that differ from per-op rounding. The
machine rounds every op to the operand type — no fusion, no extra
precision (the FloatBits kernel).

## 2. Evidence

### SPEC (go1.26.5, §Floating-point operators)

> "An implementation may combine multiple floating-point operations
> into a single fused operation, possibly across statements, and
> produce a result that differs from the value obtained by executing
> and rounding the instructions individually. An explicit
> floating-point type conversion rounds to the precision of the
> target type, preventing fusion that would discard that rounding."

With the spec's own FMA-allowed examples (`r = x*y + z` etc.). The
latitude is per-expression-DAG rewriting — not a per-op coin.

### GC probes (`docs/evidence/2026-08-15-dossier-r4/`, verbatim)

- fma-shape (x=y=1+2^-27, z=-(1+2^-26)): `x*y + z = 0` — per-op
  double rounding, NOT fused; `math.FMA(x,y,z) =
  5.551115123125783e-17` (= 2^-54) witnesses the fused value the
  narrowing excludes.
- float32-precision (a=2^24): `a + 1 + 1 == a` — per-op float32
  rounding, no extended intermediates.

The oracle platform (linux/amd64, default GOAMD64=v1 — no FMA
instruction in the base ISA) realizes the machine's exact point.

### Transfer-scope boundary (recorded; the sharp edge)

gc/arm64 (FMA in the base ISA — the compiler emits fused ops for the
spec's allowed shapes) and amd64 GOAMD64=v3 executions of fusable
shapes are OUTSIDE the envelope. The narrowing is a PLATFORM-scoped
singleton: theorems over fusable float shapes transfer only to the
oracle platform. Tripwire: `floats/fma-shape` goes red if the pinned
oracle ever fuses.

### Corpus / de-facto spec

Numerical Go code broadly ASSUMES per-op rounding (test suites
hard-code per-op results and break on arm64 — a known recurring class
of portability bug reports; local knowledge, UNVERIFIED). The spec's
explicit-conversion escape (`float64(x*y) + z` prevents fusion) is
the idiom deployed code uses to force portability. De-facto pressure
is real in both directions: much code silently depends on the
unfused point; the Go team explicitly refused to forbid fusion.

### XIMPL

NOT-OBTAINED as runtime data (arm64/v3 runs need hardware this lane
lacks; cross-compilation cannot produce runtime outputs). The
recorded scoping already treats arm64 as a known-different platform
rather than an unknown.

## 3. Proposed disposition

**KEEP the platform-scoped singleton + tripwire; re-envelope only
when a supported target requires fusable shapes** — the inventory's
judgment, affirmed with the discriminating probes now committed.

- ARGUMENT: the choice space is whole-DAG rewritings (the spec's
  cross-statement examples), so a Choices site is wrong-shaped — the
  recorded reason stands; a per-site fused/unfused choice at
  frontend-identified fusable shapes is HIGH cost with zero corpus
  benefit today (no corpus case is fusable-shape-sensitive except
  the tripwire itself, by design). The honest scope sentence
  ("linux/amd64 GOAMD64=v1") plus the tripwire is the correct
  posture while the oracle is one platform.
- COUNTER-ARGUMENT: the north star or a future target may carry
  fusable shapes whose theorems users will read as platform-neutral.
  REBUTTAL: the exposure is bounded by the frontend's reach —
  a FUSABLE-SHAPE DETECTOR (flag `a*b + c` float shapes without
  explicit conversions) could cheaply convert silent platform
  scoping into a per-program visible note; this dossier records that
  option for the ruling WITHOUT proposing it as required (it is a
  nicety until a float-heavy target exists).
- WHAT WOULD CHANGE THE ANSWER: an arm64 oracle lane (then the
  envelope becomes two-realization and the membership treatment
  applies); a target with fusable float shapes; gc emitting FMA at
  a future GOAMD64 default (tripwire fires).

## 4. Evidence gaps
