## 1. Q-INITSPAWN — `go` during `$pkginit`

**Reds in hand (1):** `goroutines/spawn-in-init/in-init`
(stage `lean-observation` — the runtime `.unsupported` surfacing as an
observation diff).

**The question.** When a `go` statement executes during package
initialization, what envelope do the spawned children get relative to
(i) the remaining initialization work — later variable initializers,
later `init` functions, later packages — and (ii) `main`'s start? The
machine currently refuses: `$pkginit` runs on the SEQUENTIAL driver,
whose spawn arms throw
`.unsupported "go spawn outside the thread pool …"` after evaluating
the callee and arguments (`GoLean/GoCore/StepFn.lean`,
`goCalleeK`/`goArgsK` arms, ~:511–531; refusal census'd at inventory
§5).

**Why it is first.** Slice 3(a) of this arc makes `$pkginit`
schedule-bearing for the init-ORDER envelope (C1/E7/L-011). That
surgery and this question touch the same phase of the machine; ruling
Q-INITSPAWN now means slice 3(a)'s design can avoid foreclosing it (or
deliberately take it along), instead of a second `$pkginit` surgery
later.

**Spec text (the envelope argument).** spec#Package_initialization:

> "Package initialization—variable initialization and the invocation
> of init functions—happens in a single goroutine, sequentially, one
> package at a time."

> "An init function may launch other goroutines, which can run
> concurrently with the initialization code. However, initialization
> always sequences the init functions: it will not invoke the next one
> until the previous one has returned."

Forced points: init itself is one sequential goroutine; init-function
sequencing is absolute; the `go` statement's HB edge holds as
everywhere (mem#go: the go statement is synchronized before the
child's start). Latitude: everything about WHEN children run. "Can run
concurrently with the initialization code" licenses during-init
interleaving; the spec's total scheduling silence (C1) equally
licenses a schedule that never runs the child until after `main`
starts. Evidence classes: SPEC (the quoted sentences) + the C1
silence, exactly C1's form.

**Envelope.** From the spawn boundary onward, init-spawned children
are ORDINARY goroutines in the runnable set; the init goroutine is one
goroutine among them (the one that later becomes/starts main), and
every registry boundary during the remaining init work is an L1
consultation point. Width: |runnable| per boundary — no new choice
site; this is C1's site gaining consultation points during the init
phase, the C8 pattern. The "children parked until main starts" point
and the "child runs immediately" point are both members (schedules
that never/always pick the child); neither is the envelope.

**Probe (new, discriminating —
`docs/evidence/2026-08-21_w32-qrow-probes/`).** The case-in-hand
cannot discriminate during-init execution (its main blocks until the
child runs, whenever that is). The directed probe — child sends on a
buffered channel, init burns registry-free work then polls with
`select`+`default` before returning — shows gc running the child
DURING init 20/20 at default GOMAXPROCS and 20/20 at GOMAXPROCS=1
(async preemption of the registry-free loop). Lower-bound consequence:
a model that releases children only at `main`'s start excludes an
observed behavior — `observed ∉ modeled`, definitionally a bug. The
cheap implementation shortcut is foreclosed by measurement, not taste.

**Options.**

- **(a) Init on the pool.** `$pkginit` executes as goroutine 0's first
  phase on the pool; `go` during init is the ordinary spawn pool step
  (`.spawned` boundary, B1/B2 boundaries apply as everywhere).
  Envelope above, verbatim. Sequential-program conservation is
  structural: with no spawn, |runnable| = 1 at every init boundary and
  the stream is never consulted (the C8/conservation-theorem hinge),
  so strict-lane init behavior is unchanged. This is also the natural
  substrate for slice 3(a)'s schedule-bearing `$pkginit`.
- **(b) Sequential init + deferred release.** Keep the sequential
  driver; collect spawns; release them to the pool at `main`'s start.
  REFUTED as a fidelity option by the probe (during-init observation
  shapes exist and gc realizes them 40/40). Only honest as a continued
  refusal of the observation shapes — i.e. it collapses into (c) with
  extra machinery.
- **(c) Defer.** Keep the refusal. Honest; the red stays; slice 3(a)
  must then take care not to build a `$pkginit` shape that makes the
  later lift harder (its design note records the interface).

**Effect on the red.** (a): `spawn-in-init/in-init` flips green strict
(its observable is deterministic — main blocks until the child's
send). (b)/(c): stays red.

**Recommendation: (a),** ruled now, implemented as a rider on (or
immediately after) slice 3(a)'s `$pkginit` surgery — one shared
surgery instead of two. Tradeoff: the pool-resident init phase must
keep init-function sequencing forced (trivially true — one goroutine's
program) and costs the slice-3 designer the spawn arm + one baseline
row; against that, (c) leaves a probed observed-∉-modeled class
standing behind a refusal, which is honest but is exactly the kind of
recorded debt this arc exists to burn down. North-star note, honestly:
etcd-io/raft's only non-test `init` is protobuf registration — no
spawn — so there is no raft demand; the demand is coherence with
slice 3(a).

**Scope: M** (machine-side only: `$pkginit` phase onto the pool or a
pool hand-off, the spawn arm, conservation argument replayed for the
init phase, 1 baseline row, one membership row for a during-init
observation shape — the probe program is the mold). Frontend
untouched. Mirror: unaffected (concurrency shape).

**DECISION BLOCK (Q-INITSPAWN).**
- **Rule A** — adopt envelope (a) (children are ordinary goroutines
  from the spawn boundary; init = one sequential goroutine; zero new
  choice sites): slice 3(a)'s design note takes the interface, the
  implementation rides that surgery or its own post-launch slice.
  *Recommended.*
- **Rule B** — defer entirely: red stays; slice 3(a) records the
  non-foreclosure interface; the probe record stands as the trigger
  for whoever lifts it.
- Either way: no strict-lane pin of during-init timing is ever
  admissible (it is latitude); the observation shape gets a membership
  row when lifted.

## 2. Q-ATOMIC — sync/atomic and mem#atomic's SC

**Reds in hand (5):** `sync/atomic-frontier/{add-load-store,cas,swap}`
(frontend-export), `sync/atomic-frontier/value` (lean-observation),
`sync/atomic-frontier/mp-litmus` (membership — the model pin: admitted
{0, 1, 11}, SC-excluded 10; gc sample 400/400 → 0).

**The question.** What realizes mem#atomic's sequential consistency in
the machine (inventory U-6)? Concretely three sub-decisions: step
granularity (are atomic ops single fused registry steps?), boundary
placement (do they take B1's `.opDone`?), and detector footprint
(atomics synchronize; atomic/plain mixtures per mem#restrictions).
Plus the claim-class consequence: atomics are THE race-free spin-wait
enabler, so the FairStream liveness tier (parked to "the atomics arc"
since sync design D5) comes due with them.

**Why it is second.** The charter names "the charter's atomics arc" as
this row's owner; the atomics arc is also the FairStream gate that the
channel-logic resume's liveness story and Q-TRYLOCK both sit behind.
Ruling the design now turns that arc from a question into execution.

**Memory-model text (the envelope argument).** mem#atomic, verbatim
(pinned go1.26.5 `go_mem.html`):

> "The APIs in the sync/atomic package are collectively 'atomic
> operations' that can be used to synchronize the execution of
> different goroutines. If the effect of an atomic operation A is
> observed by atomic operation B, then A is synchronized before B.
> All the atomic operations executed in a program behave as though
> executed in some sequentially consistent order."

> "The preceding definition has the same semantics as C++'s
> sequentially consistent atomics and Java's volatile variables."

This is a FORCED point, not latitude: U-6 records the gomm rationale —
a conforming implementation may NOT weaken these to acquire/release.
So the machine owes exactly SC, no more (weaker outcomes would be
too-wide against the quoted mandate — one of the rare places the text
gives us an upper bound directly), no less (SC-excluded outcomes like
mp-litmus's 10 must stay excluded). The latitude AROUND atomics is the
surrounding-plain-access question, owned by mem#restrictions (quoted
in memo 4) and the racy-refusal doctrine (C10).

**Design (option A, the recommended shape).**

- **Fused single-step ops, zero new choice sites.** Each sync/atomic
  op (Load/Store/Add/Swap/CompareAndSwap over the int/uint/pointer
  families) is ONE registry op: read-modify-write at a boundary,
  joining `Config.atBoundary` and taking B1's `.opDone` completion
  marker like every registry op (anything else re-creates the wedge
  class for atomics). SC then falls out of L1: an interleaving of
  atomic single steps IS an execution "as though executed in some
  sequentially consistent order" — the SC total order is the execution
  order. The envelope claim is that L1-over-fused-atomic-steps admits
  exactly the SC-consistent outcome set: ⊇ because any SC order of the
  ops is realized by the L1 schedule that runs them in that order
  (C1's width), ⊆ because each op is one indivisible step, so no
  non-SC mixing is expressible. Which SC order occurs is C1's
  scheduling latitude, already enveloped. Zero new `ChoiceSite`
  constructors — the C8 precedent, and the census stays 8 sites.
- **Frontend surface.** Atomic calls are calls, so the existing ANF
  hoist statement-anchors them; the lowering is a new op family in the
  `syncStmt` mold but VALUE-RETURNING (Load/Add/Swap/CAS return —
  unlike the sync ops, so the op family carries a result slot).
  Typed atomics (`atomic.Int32` etc.) ride the same lowering (the
  ledger's recorded judgment); `atomic.Value` is a second wave (it
  stores interface values — boxing rules, its red is already
  distinct).
- **Detector footprint.** Atomic accesses synchronize among themselves
  (the mem#atomic edge above — implemented as HB edges at the op,
  targeted at TSan's REALIZED edge set per register #13, our standing
  detector doctrine); an atomic access still counts as an ACCESS
  against plain accesses to the same location, so atomic/plain
  mixtures refuse per C10 exactly as `-race` reports them. No detector
  doctrine change — one new access kind in the footprint.
- **FairStream (the claim-class half).** An atomic spin-wait is
  RUNNABLE forever on unfair schedules — ∀-stream termination is
  honestly FALSE for it, and the dossier (§4.2, §Final synthesis) is
  unambiguous that the language does not promise eventual scheduling,
  so this is not a modeling defect to fix but a quantifier to add: the
  additive `FairStream` certification class
  (`docs/2026-08-07_fairness-precision-note.md`), whose
  non-vacuity B2's back-edge boundaries already secured. The arc ships
  atomics + the FairStream tier together, or ships atomics with
  spin-wait cases honestly outside the ∀-stream class until the tier
  lands — either is coherent; silently claiming termination is not.

**Options.**

- **(A)** As designed above: fused SC steps, zero new sites, TSan-edge
  detector footprint, `.opDone` boundaries, integer core first +
  mp-litmus, `atomic.Value` second wave, FairStream tier in the same
  arc. Effort L (the arc the charter already names).
- **(B)** Weaker-than-SC modeling of any kind — REJECTED on the quoted
  text; recorded here only so nobody re-derives it.
- **(C)** Defer the whole family. Honest; 5 reds stay; the FairStream
  tier stays parked; Q-TRYLOCK (memo 5) stays parked with it;
  channel-logic's liveness story waits.

**Effect on the reds.** (A): `add-load-store`, `cas`, `swap` flip
green strict (deterministic observables); `mp-litmus` flips green
MEMBERSHIP with the certified set {0, 1, 11} and 10 mechanically
excluded — the row's whole point, and the first executable check that
our SC realization is neither wide nor narrow at this shape; `value`
flips in the second wave. (C): all 5 stay red.

**F4 non-foreclosure.** Q-ATOMICITY (expression-step granularity,
BUG-002's latent class) is F4-owned. Option (A) stays out of its blast
radius by construction: atomic ops are statement-anchored by the ANF
hoist and fused, so no expression-position atomic step exists for a
future expression-machine reshape to split. State this in the arc's
design note; nothing here decides F4's question.

**Scope: L** — frontend wire + NativeToIR (new op family with result
slot), GoCore ops + boundaries, detector access kind + edges,
enumerator bounds (the fused step branches only via L1 — no per-op
width), the FairStream tier design, probes for the panic surface (nil
pointer, unaligned — the twice-burned rule), red-first cases beyond
the 5 in hand. Mirror: unaffected.

**DECISION BLOCK (Q-ATOMIC).**
- **Rule A** — ratify design (A) as the atomics arc's charter-level
  shape (fused SC steps, zero new sites, TSan-realized edges,
  integer-core-then-Value scope, FairStream tier bundled).
  *Recommended.*
- **Rule A′** — (A) but FairStream tier split into its own gated arc
  (atomics land; spin-wait cases stay honestly unclaimable until the
  tier). Legitimate if arc-size is the concern.
- **Rule C** — defer entirely: 5 reds stay; Q-TRYLOCK and the
  channel-logic liveness story inherit the wait.

## 3. Q-SELSEL — select↔select rendezvous

**Reds in hand (2):** `channels/select-select/core`
(lean-observation), `channels/select-select/beside-loop` (nondet —
the invariance guard trips where the refusal is stream-dependent).

**The question.** When an executing select's clause would rendezvous
with a waiter that is itself a PARKED select, which side's offer
commits, and what do the L2/L4 envelopes become for symmetric pairing
— without inventing the global arbiter gc builds out of its
channel-lock ordering? Today `selectArrivalCases` throws
`.unsupported "select-with-select rendezvous (unmodeled this slice)"`
(`GoLean/GoCore/Multi.lean:804/:813`; `applyPairing` guards at
:969/:987; refusal declared at Multi.lean:98–99).

**Why it is third.** This is the north star's core communication
idiom: etcd-io/raft's node layer pairs client-side selects
(`case n.recvc <- m:`, `deps/raft/node.go:517`; propc, confc likewise)
against `run()`'s big receive select (`node.go:386`). The raft W-lane
hits this wall the day it climbs from tracker/quorum to the node
layer. Also: the pairing machinery is warm — slice 1 just reshaped its
boundary structure.

**Spec text (the envelope argument).** spec#Select_statements step 2
(C6's quote, the entire normative basis — the memory model has no
normative select rule, per C6's recorded absence):

> "If one or more of the communications can proceed, a single one that
> can proceed is chosen via a uniform pseudo-random selection."

Both selects are "choosing"; the channel blocking rules
(spec#Send_statements, spec#Receive_operator) force the two chosen
communications to MATCH (same channel, opposite directions). The spec
says nothing about a cross-select commitment protocol — which pairs
are reachable is scheduling-plus-choice latitude. Per the doctrine's
possibilistic rule (requirement 3), "uniform pseudo-random" enters as
"any" on each side.

**Envelope.** The outcome set of one rendezvous is the set of pairs
(arriving ready clause c₁, matching parked-select clause c₂) — every
pair admitted, no distributional claim. WHICH parked select (among
several) supplies c₂ is C5's waiter envelope (width = #matches, select
clauses counted individually — already C5's stated counting rule).

**Options.**

- **(A) Asymmetric-arrival commit (extend the existing structure).**
  The arrival path already enumerates one outcome per ready clause
  (the L2 arrival-path site) and a waiter pick per matched waiter (the
  L4 site, clauses counted individually). Lift the `isSelect` refusal:
  a parked-select waiter becomes an ordinary L4 candidate identified
  by (thread, its matching clause); the pairing commits BOTH sides in
  one pool step — the arriving side at its L2-picked clause, the
  parked side at the matched clause, C7's commit-by-waking-event
  argument extended verbatim (the parked select is committed by the
  event that wakes it; no second L2 draw on the parked side). The
  machine's step atomicity IS the arbiter gc builds with lock
  ordering — we get it free. Width: unchanged sites, existing bounds
  (L2 = ready count, L4 = match count); zero new `ChoiceSite`
  constructors.
- **(B) Symmetric wake-path draw.** Add an L2 draw on the parked side
  at wake. At a rendezvous the parked side can only proceed on clauses
  matching the arrival, and each such clause is already a distinct L4
  candidate under (A) — so (B) adds NO outcome (A) lacks; it is (A)
  plus C7's general wake-path re-envelope, which stays separately
  recorded (register #12, re-argue on wake-machinery changes). Not a
  competing option, a decomposition argument for why (A)'s width is
  the full envelope.
- **(C) Defer.** Keep the refusal; 2 reds stay; record explicitly that
  the raft node layer is blocked on this row so the W-lane finds the
  dependency, not the wall.

**Effect on the reds.** (A): `core` flips green (strict if its
observable is choice-invariant, else membership — the implementation
slice classifies red-first); `beside-loop` flips to
membership/confluent (its `nondet` stage today is the invariance guard
seeing stream-dependent refusal — "default stream commits the
cell-ready clause; adversarial streams hit the refusal",
`baselines/untriaged-ids` justification block — exactly the class that
must land in an enumerating lane, never strict). (C): both stay red.

**Recommendation: (A),** post-launch, as its own small slice — the
highest-value de-refusal in the queue by north-star demand. Tradeoff:
the resume-at-a-clause commit path is new code on the trust surface
(a `resumeThread` variant taking the matched clause instead of the
head-commit scan) and `applyPairing` grows select×select transfer
arms — against 2 reds today and a hard W-lane dependency tomorrow.

**Scope: M** — `PairTarget` already carries `isSelect`; work =
candidate identification (thread × clause), the clause-directed resume
commit, `applyPairing` select×select arms (both transfer directions),
detector edges (rendezvous racesync + the BUG-046 select-send
chan-object read already exist — extend to the new pairing arms),
enumerator bounds unchanged in kind, witnesses re-checked. Mirror:
unaffected.

**DECISION BLOCK (Q-SELSEL).**
- **Rule A** — adopt envelope + option (A); implementation is a
  post-launch slice, sequenced before the raft node layer.
  *Recommended.*
- **Rule C** — defer: the refusal stands; the raft-lane dependency is
  recorded in the routing row either way.
- Interaction to note when ruling: none with C7's narrowing — (A)
  neither widens nor depends on the wake-path draw; register #12's
  re-argue trigger ("wake machinery changes") FIRES at implementation
  time, so the slice re-states C7's coverage argument as part of its
  envelope statement.

## 4. Q-RACEPATH — value-path composite read footprint (BUG-041)

**Reds in hand (1):** `race/free/array-read-write`
(lean-observation) — race-free Go refused: a value-path array-element
read (`a[1]`) records a WHOLE-CELL read, colliding with a concurrent
disjoint-element write.

**The question.** Race-footprint granularity for value-path composite
reads: the model loads the whole composite cell at `evalVar`/`.deref`
and projects afterwards, so the footprint is the whole cell except
where the shipped `fieldGet`-chain narrowing applies
(`fieldChainTarget`, `GoLean/GoCore/Race.lean:418–433`; the O1
inventory entry at Race.lean:60–79). Array-element reads are NOT
narrowed — "the index is unevaluated when the base is read" — hence
the red pin. Fail-closed today: over-refusal, never a missed race.

**Why it is fourth.** Small, precision-only, and adjacent to slice 4's
footprint territory (the E9 cross-goroutine question and the parked
Q11 entry-identity stamps live in the same file); a ruling now lets it
ride any footprint-touching slice.

**Memory-model text.** The footprint question is NOT an envelope-width
question — the refusal boundary is doctrine (C10) and the detector
targets TSan's realized edge set (register #13). Two texts bear:
mem#restrictions' per-sub-value license (the normative ground under
O1, quoted at C10's anchor):

> "A read of an array, struct, or complex number may be implemented as
> a read of each individual sub-value (array element, struct field, or
> real/imaginary component), in any order."

— i.e. the language itself decomposes composite reads into sub-value
reads, so an ELEMENT-precise footprint is the faithful one; and the
oracle side: gc compiles `a[1]` to a single element load and `-race`
instruments exactly that, so the whole-cell record is strictly
stronger than the oracle's — the red pin is TSan-green/ours-red, the
recorded fail-closed direction.

**Options.**

- **(A) Constant-index narrowing.** Extend `fieldChainTarget`'s
  pattern to `indexGet` frames whose index operand is already a value
  (a literal or an ANF-hoisted temp whose value is in the frame):
  narrow the base read to the element path. Covers the case in hand
  (`a[1]`); dynamic-index reads stay whole-cell, recorded in O1 as the
  narrowed residual. Effort S; same shape as the shipped fieldGet
  narrowing, same green-guards pattern
  (`race/free/{field-read-write,ptr-field-read-write}` are the mold).
- **(B) Deferred-footprint recording.** Delay the composite read's
  footprint until the projection applies, computing the element path
  with the EVALUATED index — covers dynamic indices too. Effort M and
  touches the `stepAccesses` architecture; the panic window (index out
  of range between base read and projection) needs its own footprint
  argument; fail-closed fallback on every unrecognized shape. Only
  worth it if a real target needs dynamic-index disjointness — and the
  north-star does not: raft's hot indexing is on SLICES, whose element
  reads are address-based and already precise; the O1 class is
  value-path ARRAYS.
- **(C) Defer.** O1 already records the over-approximation honestly;
  the red pin stands.

**Effect on the red.** (A) and (B): `race/free/array-read-write` flips
green (its index is the literal 1); the existing green-guards keep the
narrowing honest. (C): stays red.

**Recommendation: (A)** — S, the precise fix for the exhibited class,
with (B) explicitly NOT taken until a target exhibits the
dynamic-index shape (record that trigger in O1). Tradeoff: (A) leaves
a recorded residual; (B) buys generality no consumer needs at real
architectural cost.

**Scope: S** — Race.lean only (`fieldChainTarget` generalization +
O1 text update), 1 baseline row, no envelope statement owed (footprint
precision inside a doctrine-decided boundary, not latitude width).
Mirror: N/A (detector is pool-side).

**DECISION BLOCK (Q-RACEPATH).**
- **Rule A** — take (A) at the next footprint-touching slice (slice 4
  is the natural vehicle). *Recommended.*
- **Rule C** — defer: the red pin and O1 stand as-is.
- Non-question, recorded: nobody proposes weakening the refusal
  boundary itself — C10 is doctrine and not this memo's to touch.

## 5. Q-TRYLOCK — TryLock, spurious failure, and the FairStream class

**Reds in hand (1):** `sync/out-of-scope-trylock/trylock-uncontended`
(frontend-export). Note honestly: the case's main DISCARDS the
result — its observable is exit-0 only; it is a refusal marker, not an
envelope witness. A real TryLock model owes a result-observing case,
which CANNOT be a strict pin (next paragraph).

**The question.** TryLock's return-value envelope and its claim class:
mem#locks grants an EXPLICIT spurious-failure member, and TryLock
retry loops are spin-waits whose termination is fairness-dependent —
the FairStream certification-class question that kept TryLock out of
the sync slice by design (sync design §6/§9).

**Memory-model text (the envelope argument).** mem#locks, verbatim:

> "A successful call to l.TryLock (or l.TryRLock) is equivalent to a
> call to l.Lock (or l.RLock). An unsuccessful call has no
> synchronizing effect at all. As far as the memory model is
> concerned, l.TryLock (or l.TryRLock) may be considered to be able to
> return false even when the mutex l is unlocked."

This is spec-DECLARED latitude, not silence: at an unlocked mutex the
return-value envelope is {true, false}. A deterministic
success-when-free model would pin a latitude the text grants by name —
the one narrowing class the doctrine treats as worse than a
spec-silent pin, and gc itself realizes false-when-momentarily-free
under contention history, so the pin would not even track the oracle.

**Design (when modeled).** TryLock is the first op that needs a NEW
`ChoiceSite` (unlike C8's zero-site rule): at the apply, width 2 when
the cell is acquirable (acquire | spurious false; empty-stream default
= acquire, so strict-lane uncontended behavior matches gc's realized
point), width 1 (forced false) when held. Successful acquire takes the
Lock HB edge (the "equivalent to a call to l.Lock" sentence);
unsuccessful takes NOTHING ("no synchronizing effect at all" — the
detector must NOT add an edge on failure). Fairness non-preclusion
holds trivially (the site is not a scheduling pick). Result-observing
cases are membership rows over {true, false} at acquirable states.
Termination: a TryLock retry loop is runnable forever — ∀-stream
termination honestly FALSE; the FairStream tier (Q-ATOMIC's arc) is
the certification home, and B2's back-edges already make the
quantifier non-vacuous.

**Options.**

- **(A) Model now, standalone**: the site + membership rows, with
  spin-wait cases honestly outside the ∀-stream class until FairStream
  lands. Effort M; delivers 1 red and a modeled member nobody
  currently consumes.
- **(B) Model narrowed (always-succeed-when-free), no site.** Rejected
  above: pins a spec-DECLARED latitude to dodge one width-2 draw.
  Recorded so nobody re-derives it.
- **(C) Defer into the atomics arc**, pre-ruling the envelope now:
  when modeled, TryLock takes the spurious-failure choice site (A)'s
  shape — never (B) — and its termination claims live in the
  FairStream tier. The red stays until that arc.

**Effect on the red.** (A): flips green strict (exit-0 observable —
even a spurious-false stream exits 0). (C): stays red until the
atomics arc.

**Recommendation: (C)** — the sync design parked TryLock exactly here
for the class-boundary reason, and nothing has changed except that B2
made the eventual FairStream tier non-vacuous. Pre-ruling the envelope
costs nothing and prevents the (B) shortcut from ever looking
tempting. Tradeoff: one red carried for arc coherence.

**Scope (when taken): M** — one `ChoiceSite` constructor + policy row,
`applySyncOp` arm + detector edge asymmetry, membership rows,
FairStream-tier coupling. Mirror: unaffected.

**DECISION BLOCK (Q-TRYLOCK).**
- **Rule C** — defer to the atomics arc WITH the envelope pre-ruled
  (spurious-failure site, success-edge-only detector, FairStream
  claim class). *Recommended.*
- **Rule A** — model standalone ahead of the arc (if a target demands
  TryLock earlier).
- **Anti-rule, recorded**: (B) is not on the menu at any date.

## 6. Q-SYNCVAL — sync ops as first-class values

**Reds in hand (5):**
`sync/iface-dispatch/{mutex-user-iface,wg-user-iface,locker-box-dispatch}`,
`sync/escapes/{method-value,go-stmt}` — all frontend-export.
(The other two `sync/escapes` rows — `promoted`, `defer-embedded` —
were LIFTED by W4.1 item 5 and are green; the suite comments record
it.)

**The question.** Does a sync op's scheduler-step identity survive
indirection — must a dispatched `Lock()` (interface dispatch, method
value, `go`-position callee) consume the SAME C8 acquisition
site/boundary as a direct `m.Lock()` — or does the surface stay
refused? Today: satisfaction and boxing answer correctly through
declaration-only stubs (`syncMethodStubs`,
`tools/nativefrontend/emit.go` ~:5322–5400); every CALL through a stub
refuses per-stub, method values refuse at ~:5452, expression-position
ops at ~:7348 (the ledger's recorded :4739/:4679 anchors have drifted
with the file; the constructs are these).

**Text (the argument is composition, not latitude).** spec#Method_values
and spec#Interface_types make indirection semantics-preserving — a
method value or dispatched call denotes the same method with the same
receiver; the sync DOCS sentences quoted at the arms are per-METHOD
contracts indifferent to call path (mem#more's delegation: "The
documentation for each of these specifies the guarantees it makes
concerning synchronization"). So there is no envelope question here at
all: the ONLY sound modeled semantics is identity — a dispatched op
consumes the same `applySyncOp` boundary, same C8 envelope, same
detector edges as the direct form. The question is purely
implement-vs-refuse, and the identity principle is the thing worth
ruling: **indirection must preserve op identity or refuse — never a
variant semantics.**

**The recorded plan.** Sync design §12 P-S2-6, verbatim in substance:
real stub BODIES over the machine's existing sync ops (Lock/Unlock/
RLock/RUnlock/Add/Done/Wait as one-statement bodies; Do via a generic
`$syncOnceDo`; TryLock/TryRLock/RLocker/Go stay declaration-only —
TryLock per memo 5) — "semantics-identical to direct calls at registry
granularity". A method value over a stub-with-body is an ordinary
closure; a `go m.Lock()` callee is the stub body. Granularity note for
the audit trail: the extra call frame adds PRIVATE steps only — no new
boundaries, no observable widening at registry granularity.

**Options.**
- **(A) Implement P-S2-6** as its own post-launch slice with red-first
  cases (the note already scoped it as "a scoped slice, not a
  fix-round rider"). Frontend-only — GoCore untouched (the bodies are
  ordinary functions lowering to existing `syncStmt` ops).
- **(C) Defer.** 5 reds stay; every raft-adjacent `sync.Locker`
  abstraction stays refused.

**Effect on the reds.** (A): all 5 flip green strict (deterministic
observables). (C): stay red.

**Recommendation: (A)** — the plan exists, the risk is low (no
semantic-core change), and 5 reds is the largest single-slice flip in
this document. Tradeoff: essentially none beyond slice budget; the
one discipline item is that the stub bodies must be audited as
frontend surface (they synthesize code), which the P-S2-6 scoping
already demands.

**Scope: M** (frontend stub-body emission + the method-value and
go-position paths + cases; zero GoCore/detector change). Mirror:
unaffected.

**DECISION BLOCK (Q-SYNCVAL).**
- **Rule A** — ratify the identity principle (same site or refuse) and
  green-light P-S2-6 as a post-launch slice. *Recommended.*
- **Rule C** — defer; the identity principle should be ruled anyway so
  any future lift is bound by it.

## 7. Q-SYNCLIT — composite-literal construction of sync primitives

**Reds in hand (2):**
`sync/composite-literal/{mutex-addr-lit,waitgroup-value-lit}` — both
frontend-export (`&sync.Mutex{}` and `sync.WaitGroup{}`; refusal at
`tools/nativefrontend/emit.go` ~:5950–5958, "composite-literal

**The question.** What does constructing (the ledger adds: copying) a
sync primitive by composite literal mean — model or keep refused? The
charter's OQ3 asked memo-vs-named-ruling; this memo is deliberately
short because the question dissolves under the spec text.

**Text.** spec#Composite_literals:

> "It is an error to specify an element for a non-exported field of a
> struct belonging to a different package."

All four modeled primitives have only non-exported fields, so the
ENTIRE legal cross-package literal surface is the EMPTY literal —
whose value is the zero value, and the zero value is the ready
primitive by documented contract ("The zero value for a Mutex is an
unlocked mutex", sync docs; same for the others, already the modeled
`Ty.sync` zero). The COPY half of the ledger's phrasing is already

construction-surface plumbing with NO latitude: `sync.Mutex{}` ≡ the
zero value ≡ what `var`/`new` already construct.

**Options.**
- **(A) Implement:** the frontend lowers the empty composite literal
  (value and `&`-of forms) of the four modeled kinds to the same
  zero-value construction as `var`/`new`; any non-empty sync literal
  keeps failing closed (unreachable cross-package anyway). Effort S,
  emit.go only.
- **(C) Defer:** 2 reds stay for a lowering whose semantics is forced.

**Effect on the reds.** (A): both flip green strict. (C): stay red.

**Recommendation: (A)** — S, forced semantics, no envelope statement
owed (zero value is a forced point). The only real content of the
ruling is confirming the reduction above so the refusal comment stops
implying an open semantic question.

**Scope: S** (emit.go lowering + 2 baseline rows). Mirror: N/A
(frontend only).

**DECISION BLOCK (Q-SYNCLIT).**
- **Rule A** — take the S lowering at any convenient post-launch
  slice (natural rider on the Q-SYNCVAL slice). *Recommended.*
- **Rule C** — defer; record in the suite comment that the semantics

## 8. Q-COND — sync.Cond's wakeup envelope

**Reds in hand (3):**
`sync/out-of-scope-cond/{cond-signal-no-waiter,cond-wait-signal,cond-broadcast}`
— all frontend-export (`sync.Cond` fails closed at the wire.go sync
switch, `tools/nativefrontend/wire.go` ~:389–398: only
Mutex/RWMutex/WaitGroup/Once are modeled). The two Q-COND rows were
built to normalize wakeup order away, so they flip STRICT under any
conforming Cond model — deliberately.

**The question.** sync.Cond's wakeup envelope: which waiter Signal
wakes, what Broadcast's wake set and resumption order are, whether
spurious wakeups are admitted, and where Wait's re-acquisition
ordering sits — and whether to model Cond at all.

**Text (DOCS is the normative class here — the spec is silent and
mem#more delegates: "The documentation for each of these specifies the
guarantees it makes concerning synchronization"). All from the pinned
`sync/cond.go`:**

> "Wait atomically unlocks c.L and suspends execution of the calling
> goroutine. After later resuming execution, Wait locks c.L before
> returning. Unlike in other systems, Wait cannot return unless awoken
> by [Cond.Broadcast] or [Cond.Signal]."

> "Signal wakes one goroutine waiting on c, if there is any."

> "Signal() does not affect goroutine scheduling priority; if other
> goroutines are attempting to lock c.L, they may be awoken before a
> 'waiting' goroutine."

> "Broadcast wakes all goroutines waiting on c."

> "Cond arranges that a call to [Cond.Broadcast] or [Cond.Signal]
> 'synchronizes before' any Wait call that it unblocks."

> "A Cond must not be copied after first use."

**The envelope, argued from those sentences.**
- **NO spurious wakeups.** "Wait cannot return unless awoken by
  Broadcast or Signal" is a documented exclusion — one of the rare
  places the text hands us the UPPER bound directly. An envelope
  admitting spurious wakeups would be too WIDE by contract, not
  conservative; the loop-recheck idiom absorbing them is irrelevant to
  what the model may admit. This memo's most important sentence.
- **Signal's waiter choice: any waiter** (width = #waiters). "Wakes
  one goroutine … if there is any" says nothing about which; gc's
  FIFO notifyList is one legal point.
- **Broadcast's wake set: forced (all waiters).** Resumption ORDER is
  not a Cond question at all: each woken waiter must re-acquire c.L,
  so ordering collapses into the existing C8 acquisition envelope —
  and the Signal priority disclaimer (dossier §3.5) explicitly
  licenses barging by lockers, so C8's
  every-registry-schedule envelope is exactly right, no new machinery.
- **HB edges**: Signal/Broadcast synchronized-before the Wait return
  it unblocks (implemented, as always, at TSan's realized edge set —
  register #13).
- **Copy is a runtime FATAL** ("must not be copied after first use",
  enforced by `copyChecker`) — unlike the four modeled primitives, a
  Cond model carries the fatal (R11's class) or fails closed on copy
  shapes; silent tolerance is not an option.

**Model shape (when built).** `CondPrim` value + a blocked-on-cond
config shape; Signal makes ONE parked waiter wake-eligible — the
waiter pick is a genuinely new latitude point: either a new
`ChoiceSite` (condSignal, width = #waiters) or reuse of the L4
waiter-pick machinery with Cond waiters as candidates. Broadcast
consumes nothing (forced set); the woken waiters' re-acquisitions ride
C8/L1. Wait's unlock-park must be atomic against a racing
Signal (the "atomically unlocks … and suspends" sentence — the
missed-wakeup window is the correctness crux and the probe suite's
first target, per the twice-burned rule §2 discipline: probe the
panic/fatal surface — Wait without holding L, copy fatal — before
building).

**Options.**
- **(A) Model** — a full new primitive: wire + NativeToIR + GoCore op
  family + wake machinery + one new choice site + detector edges +
  probe suite + cases. Effort L for a primitive with ZERO north-star
  demand (etcd-io/raft uses no sync.Cond in non-test code — verified
  against `deps/raft`) and whose only recorded consumers are two goose
  phase-2 compat files (sync design §9: `unittest/condvar.go`,
  `unittest/locks.go`).
- **(C) Defer with the envelope pre-ruled** (the four bullets above
  recorded as the binding design constraints for whoever builds it).
  3 reds stay.

**Effect on the reds.** (A): all 3 flip green strict (the suite was
built order-normalized for exactly this). (C): stay red.

**Recommendation: (C)** — pure frontier by demand; the valuable thing
today is pinning the envelope from the documented text (especially the
no-spurious-wakeup exclusion, which a naive
"condition variables have spurious wakeups" prior would get WRONG in
the too-wide direction where no oracle can catch it). Tradeoff: 3 reds
carried; the goose compat files stay blocked (they carry other
blockers anyway, per sync design §9).

**Scope (when taken): L.** Mirror: unaffected.

**DECISION BLOCK (Q-COND).**
- **Rule C** — defer with the envelope pre-ruled (no spurious wakeups;
  Signal = any-waiter width-#waiters; Broadcast = forced-all with C8
  resumption; TSan-realized HB; copy = fatal). *Recommended.*
- **Rule A** — charter a Cond slice now (only if a target outside the
  current queue demands it).
