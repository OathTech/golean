### The example

**Go** (`Corpus/coverage/exec/examples/histogram/main.go`): `histogram`
builds a `map[uint64]uint64` of counts over a `[]uint64`, reads the
count of a queried key (`counts[q]` — Go's zero value on an absent
key), then counts the map's entries with a VARIABLE-FREE
`for range counts {}`. Harness `histogram_harness_r(n, seed, q)` is the
S3 RELATIONAL style: setup family `v[i] = seed + i%3`, a copy loop into
a fixed-cap `[8]uint64`, then `histogram(v, q)` — the values AND both
summaries returned as data.

- **JC (observable choice):** both summaries returned, not one — the
  queried count exercises the map INDEX READ and `distinct` exercises
  the enveloped `for range`. The charter asked that the observable
  range over the map so the `∀ch` teaching point is real; `distinct`
  does, and its spec (`distinctCount`) is a function of the returned
  values alone. Principle: the harness ruling (returned data over a
  verdict) + the charter's order-invariance requirement.
- **JC (variable-free range):** `for range counts {}` rather than
  wordcount's `for _, c := range counts`. It is the honest lowering of
  "count the entries", and it makes the machine side markedly cheaper —
  `bindIterVars` with no binders allocates NOTHING, so the range loop is
  state-stable. Principle: velocity, where honesty is unaffected (the
  Go is what a Go programmer would write).

### The proof, in one paragraph

Entry → setup loop (57 steps/iteration, the P5 schema) → copy loop (53)
→ ONE program-consulting `enterFrame` → the subject's prologue (51) →
the counting loop (84/iteration, `Histogram/CountLoop.lean`) →
`hits := counts[q]` (the map READ, `MapMem.applyStrictOp_mapGet`, Go's
zero value on an absent key) → `distinct := 0` → the map-range loop (16
steps/iteration, one choice consumed, ZERO allocation) → the epilogue.
Two pure bridges carry the answers: `cnt_countsList'` (the map's count
at a key IS that key's number of occurrences) and `countsList_length`
(the histogram has exactly as many entries as the list has distinct
values). The second is what makes the enveloped loop's answer readable.

  delegated to a Fable worker against a fully specified theorem

## Unit G1.3 — `palin` (ArrayPalindrome) — **COMPLETE** — [lane B]

### The example

**Go** (`Corpus/coverage/exec/examples/palin/main.go`): `isPalindrome`
walks two indices inward — `i` up from `0`, `j` down from `len(s)-1` —
returning `0` at the FIRST mismatched pair and `1` if the walk meets in
the middle. Harness `palin_harness_r(n, seed)` is the S3 RELATIONAL
style: setup family `s[i] = seed + i%2`, a copy loop into a fixed-cap
`[8]uint64`, then `isPalindrome(s)` — the checked array AND the verdict
returned as data.

### THE FINDING THIS UNIT CONTRIBUTES: the two-exit loop

Every subject loop in the shipped gallery leaves ONE way, so every
shipped loop lemma ends at a loop head and the run assembly chains the
exit afterwards. `isPalindrome` leaves TWO ways that are not symmetric:
the loop's exit test (walk met in the middle → `return 1`) and a
`return 0` from INSIDE the body (first mismatch). The consequence is
structural, not cosmetic:

* `ph_loopP` runs all the way to the DRIVER TERMINAL rather than to a
  loop head, and its content is that BOTH exits deliver the same
  observable — `palinSpec l` in `$res1` either way.
* The loop's own `i`/`j` cells are EXISTENTIALLY QUANTIFIED in its
  conclusion (`∃ k iv jv, …`), because the two exits stop at different
  indices and nothing the harness returns depends on which. That is
  the honest way to say "the loop-local state is not observable"
  without inventing a normal form for it.
* The two exit segments (`ph_bailP` 70 steps, `ph_outP` 49 steps) are
  proven separately and the induction picks between them.

`twosum` (early return from a nested loop), `bubble` (the `!swapped`
early exit) and `rle` all have this shape too, which is why it is
written up here rather than left inside the example.

- **JC (loop shape):** run the subject induction to the terminal and
  existentially quantify the loop-local cells, rather than normalizing
  the two exits to a common `i`/`j`. Principle: honesty beats elegance
  — a normal form would be a fiction about where the program stopped,
  and the observable genuinely does not depend on it.
- **JC (statement strength):** the headline states `verdict =
  palinSpec pre` (a functional equation) and ships
  `palin_verdict_iff` as the FIRST-ORDER readout (`v = 1 ↔
  pre.reverse = pre`) rather than making the iff the headline.
  Principle: the statement-TCB doctrine — headline theorems ship
  first-order readout corollaries; the reader gets the form they can
  check without unfolding a definition, and the proof keeps the form
  it composes with.
- **JC (spec shape):** `palinSpec xs = if xs.reverse = xs then 1 else 0`
  — no index arithmetic in the STATEMENT at all; the half-scan
  characterisation the Go actually decides is a THEOREM
  (`palin_iff_half`), not a definition. Principle: the gallery's whole
  purpose is that the claim be readable without the algorithm.

genuinely smaller (no map, one subject loop instead of two), so this is

- **JC (the lane's tracer):** a GENERIC step tracer + continuation
  printer (`.tmp/Probe.lean`) was built before any Lean was written,
  generalizing the flagship's example-specific `.tmp/trace.lean`. It
  rebuilds `runFunctionWithContextM`'s prelude itself (`bindParams` /
  `allocDecls` / `pinResultLocs`) from a lowered program and a function
  key, so it needs ONLY the generated `*Program` module — no proof
  module, no `derive_entry_eq`, nothing that has to exist first. Every
  address, every continuation shape and every step count in this unit
  came from it, and it shipped to all five sibling worker lanes
  unchanged. Principle: `#eval` before you `decide`, applied to `rfl`
  goals. Cost: ~25 minutes; it is the single highest-leverage artifact
  this lane produced that is not a Lean lemma.
- **JC (worktree bootstrap, recorded because it will recur):**
  `scripts/setup-deps` does NOT seed `proofs/.lake/packages`, so a
  fresh lane worktree cannot build offline. The fix used — and it is
  the project's OWN recipe, `scripts/comparator-judge:100` does exactly
  this for a fresh clone — is to copy `proofs/.lake/packages` from the
  primary checkout after verifying `proofs/lake-manifest.json` pins are
  identical. Principle: fail-closed bootstrap is right, but the
  documented escape must be the sanctioned one, and it must be checked
  against the tracked pin rather than assumed.
