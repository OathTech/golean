### The example

**Go** (`Corpus/coverage/exec/examples/histogram/main.go`): `histogram`
builds a `map[uint64]uint64` of counts over a `[]uint64`, reads the
count of a queried key (`counts[q]` — Go's zero value on an absent
key), then counts the map's entries with a VARIABLE-FREE
`for range counts {}`. Harness `histogram_harness_r(n, seed, q)` is the
S3 RELATIONAL style: setup family `v[i] = seed + i%3`, a copy loop into
a fixed-cap `[8]uint64`, then `histogram(v, q)` — the values AND both
summaries returned as data.

- **JC (observable choice):** both summaries returned, not one — the
  queried count exercises the map INDEX READ and `distinct` exercises
  the enveloped `for range`. The charter asked that the observable
  range over the map so the `∀ch` teaching point is real; `distinct`
  does, and its spec (`distinctCount`) is a function of the returned
  values alone. Principle: the harness ruling (returned data over a
  verdict) + the charter's order-invariance requirement.
- **JC (variable-free range):** `for range counts {}` rather than
  wordcount's `for _, c := range counts`. It is the honest lowering of
  "count the entries", and it makes the machine side markedly cheaper —
  `bindIterVars` with no binders allocates NOTHING, so the range loop is
  state-stable. Principle: velocity, where honesty is unaffected (the
  Go is what a Go programmer would write).

### The proof, in one paragraph

Entry → setup loop (57 steps/iteration, the P5 schema) → copy loop (53)
→ ONE program-consulting `enterFrame` → the subject's prologue (51) →
the counting loop (84/iteration, `Histogram/CountLoop.lean`) →
`hits := counts[q]` (the map READ, `MapMem.applyStrictOp_mapGet`, Go's
zero value on an absent key) → `distinct := 0` → the map-range loop (16
steps/iteration, one choice consumed, ZERO allocation) → the epilogue.
Two pure bridges carry the answers: `cnt_countsList'` (the map's count
at a key IS that key's number of occurrences) and `countsList_length`
(the histogram has exactly as many entries as the list has distinct
values). The second is what makes the enveloped loop's answer readable.

  delegated to a Fable worker against a fully specified theorem

### The proof, in one paragraph

Entry → the `mod == 0` guard (21 steps) → the `mod == 1` guard (9) →
`result := 1` and the `base % mod` apply (25 + 1) → the `$forFirst`
block to the loop head (18) → first-pass dispatch (25) → **the loop**,
by induction on the exponent's BIT BUDGET → exit (40). One iteration is
92 steps when `exp` is odd and 72 when it is even; the two branches
share a 44-step tail (`pm_iter_tail`) covering the squaring, the
halving and the next dispatch. Six `applyStrictOp` steps per iteration
are data-dependent and each is discharged by a conditioned executable
fact. Two pure bridges carry the answer: `powLoop` (the loop's own
recursion) and `powLoop_eq` (that it computes `(r · bᵉ) mod m`), so the
headline states MATHEMATICS while the induction states the loop.

### Judgment calls (this unit)

- **JC (the spec is mathematics, not the loop):** the postcondition is
  `if mod = 0 then 0 else base ^ exp % mod`, with `powLoop` confined to
  the proof layer behind `powLoop_eq`. Principle: claim ≤ theorem cuts
  both ways — a spec that merely re-describes the program is a claim
  that says nothing, and the gallery exists to be READ. Cost: the
  modular-arithmetic bridge (~45 lines).
- **JC (the domain is the SOURCE's no-wrap condition, verbatim):** the
  hypothesis is `(mod − 1) * (mod − 1) < 2 ^ 64`, which is exactly the
  condition the Go comment states, rather than a rounder `mod ≤ 2^32`.
  Principle: honesty beats elegance — the theorem's domain and the
  program's documented domain are then the same sentence, and the wrap
  region is excluded in the open rather than by a convenient constant.
- **JC (all three guard paths in ONE theorem):** `mod = 0` and
  `mod = 1` are proved as machine paths rather than excluded by
  hypothesis, so the entry covers the whole documented domain below the
  wrap threshold. Cost: two extra raw segments and two short
  compositions (~35 lines). `mod = 1` needed no case in the SPEC,
  because `base ^ exp % 1 = 0` — the guard and the mathematics agree,
  and that is worth a reader's attention.
- **JC (bit-budget induction ⇒ a CONSTANT bound):** the loop induction
  is `∀ d, exp < 2 ^ d → k ≤ 92·d + 40`, instantiated at `d = 64`,
  rather than an induction on `exp` giving a bound linear in `exp`.
  Principle: bound tightness is a delegated judgment call, and `6027`
  is both tighter and far more legible than any `c·exp` would be.
- **JC (probe-first, not guess-first — the flagship's reflex, paid
  forward):** a step tracer + structured continuation printer
  (`.tmp/pmprobe.lean`, using `deriving instance Repr for Cont, Config`)

### Lane-A self-review correction (same day, before the workers landed)

Re-checking `powmod`'s own gallery text against arithmetic rather than
memory turned up a FALSE claim of my own, now fixed in the module
docstring and the gallery entry:

- **Claimed:** "the corpus rows `wrap` and `harness-extreme` pin [the
  wrap] region [that the theorem excludes]".
- **True:** the no-wrap condition `(mod−1)² < 2⁶⁴` is `mod ≤ 2³²`.
  `harness-extreme` has `mod = 999999937 < 2³²`, so it is INSIDE the
  theorem's domain — its extremity is in `base` and `exp`, not `mod`.
  Exactly ONE of the 13 rows, `wrap` (`mod = 2⁶³ − 1`), is outside.
- The corrected text says the stronger and true thing: **12 of the 13
  differential rows lie inside the theorem's domain**, and names the one
  that does not.
- Principle: honesty beats velocity, and "which rows does the theorem
  actually cover" is a claim like any other — it needed a computation,
  not a recollection. Recorded because the original error was the easy
  kind: two rows tagged `widths` in `cases.tsv`, read as "both are in
  the wrap region", when the tag is about the arguments' width and not
  about the modulus.
