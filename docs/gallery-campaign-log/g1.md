### The example

**Go** (`Corpus/coverage/exec/examples/histogram/main.go`): `histogram`
builds a `map[uint64]uint64` of counts over a `[]uint64`, reads the
count of a queried key (`counts[q]` — Go's zero value on an absent
key), then counts the map's entries with a VARIABLE-FREE
`for range counts {}`. Harness `histogram_harness_r(n, seed, q)` is the
S3 RELATIONAL style: setup family `v[i] = seed + i%3`, a copy loop into
a fixed-cap `[8]uint64`, then `histogram(v, q)` — the values AND both
summaries returned as data.

- **JC (observable choice):** both summaries returned, not one — the
  queried count exercises the map INDEX READ and `distinct` exercises
  the enveloped `for range`. The charter asked that the observable
  range over the map so the `∀ch` teaching point is real; `distinct`
  does, and its spec (`distinctCount`) is a function of the returned
  values alone. Principle: the harness ruling (returned data over a
  verdict) + the charter's order-invariance requirement.
- **JC (variable-free range):** `for range counts {}` rather than
  wordcount's `for _, c := range counts`. It is the honest lowering of
  "count the entries", and it makes the machine side markedly cheaper —
  `bindIterVars` with no binders allocates NOTHING, so the range loop is
  state-stable. Principle: velocity, where honesty is unaffected (the
  Go is what a Go programmer would write).

### The proof, in one paragraph

Entry → setup loop (57 steps/iteration, the P5 schema) → copy loop (53)
→ ONE program-consulting `enterFrame` → the subject's prologue (51) →
the counting loop (84/iteration, `Histogram/CountLoop.lean`) →
`hits := counts[q]` (the map READ, `MapMem.applyStrictOp_mapGet`, Go's
zero value on an absent key) → `distinct := 0` → the map-range loop (16
steps/iteration, one choice consumed, ZERO allocation) → the epilogue.
Two pure bridges carry the answers: `cnt_countsList'` (the map's count
at a key IS that key's number of occurrences) and `countsList_length`
(the histogram has exactly as many entries as the list has distinct
values). The second is what makes the enveloped loop's answer readable.

## Unit G1.3 — `palin` (ArrayPalindrome) — **COMPLETE** — [lane B]

### The example

**Go** (`Corpus/coverage/exec/examples/palin/main.go`): `isPalindrome`
walks two indices inward — `i` up from `0`, `j` down from `len(s)-1` —
returning `0` at the FIRST mismatched pair and `1` if the walk meets in
the middle. Harness `palin_harness_r(n, seed)` is the S3 RELATIONAL
style: setup family `s[i] = seed + i%2`, a copy loop into a fixed-cap
`[8]uint64`, then `isPalindrome(s)` — the checked array AND the verdict
returned as data.

### THE FINDING THIS UNIT CONTRIBUTES: the two-exit loop

Every subject loop in the shipped gallery leaves ONE way, so every
shipped loop lemma ends at a loop head and the run assembly chains the
exit afterwards. `isPalindrome` leaves TWO ways that are not symmetric:
the loop's exit test (walk met in the middle → `return 1`) and a
`return 0` from INSIDE the body (first mismatch). The consequence is
structural, not cosmetic:

* `ph_loopP` runs all the way to the DRIVER TERMINAL rather than to a
  loop head, and its content is that BOTH exits deliver the same
  observable — `palinSpec l` in `$res1` either way.
* The loop's own `i`/`j` cells are EXISTENTIALLY QUANTIFIED in its
  conclusion (`∃ k iv jv, …`), because the two exits stop at different
  indices and nothing the harness returns depends on which. That is
  the honest way to say "the loop-local state is not observable"
  without inventing a normal form for it.
* The two exit segments (`ph_bailP` 70 steps, `ph_outP` 49 steps) are
  proven separately and the induction picks between them.

`twosum` (early return from a nested loop), `bubble` (the `!swapped`
early exit) and `rle` all have this shape too, which is why it is
written up here rather than left inside the example.

- **JC (loop shape):** run the subject induction to the terminal and
  existentially quantify the loop-local cells, rather than normalizing
  the two exits to a common `i`/`j`. Principle: honesty beats elegance
  — a normal form would be a fiction about where the program stopped,
  and the observable genuinely does not depend on it.
- **JC (statement strength):** the headline states `verdict =
  palinSpec pre` (a functional equation) and ships
  `palin_verdict_iff` as the FIRST-ORDER readout (`v = 1 ↔
  pre.reverse = pre`) rather than making the iff the headline.
  Principle: the statement-TCB doctrine — headline theorems ship
  first-order readout corollaries; the reader gets the form they can
  check without unfolding a definition, and the proof keeps the form
  it composes with.
- **JC (spec shape):** `palinSpec xs = if xs.reverse = xs then 1 else 0`
  — no index arithmetic in the STATEMENT at all; the half-scan
  characterisation the Go actually decides is a THEOREM
  (`palin_iff_half`), not a definition. Principle: the gallery's whole
  purpose is that the claim be readable without the algorithm.

### THE KIT-GAP LIST (rle) — recorded in full

### [lane B] KIT GAP — familyF (index-function-parameterized setup family)

**What the kit could not carry:** the harness setup family
`s[i] = seed + i/3`. `SliceMem.familyMod k` is hard-coded to
`seed + i % k`; there is no family parameterized by an index function.

**Exact shape wanted:**
```lean
def SliceMem.familyF (f : Nat → Nat) (n seed : Nat) : List Int :=
  (List.range n).map (fun i => (((seed + f i) % 2 ^ 64 : Nat) : Int))
```
with `length` / `range` / `Z_range` (prefix + zero tail) / `succ` /
`set` / `getD` proven once, plus the delegations
`familyMod k = familyF (· % k)`, twosum's family `= familyF id`, and
rle's `= familyF (· / 3)`. `SliceMem.prefixPad` already generalizes
over the family function and needed NO local re-derivation — only the
family itself is missing.

**Consumers:** rle (landed, local witness `rleFamily` in
`proofs/GoLeanProofs/Examples/RunLength/Pure.lean` — ~60 lines of
re-derived lemmas), twosum (chartered), histogram/wordcount/palin
retrofits (`familyMod` becomes the `· % k` instance).

**Cost here:** ~60 lines (`rleFamily` + 6 mirrored lemmas).

### [lane B] KIT GAP — applyStrictOp_div_u64 (the `/` executable fact)

**What the kit could not carry:** uint64 division. The kit has
`SliceMem.applyStrictOp_mod_u64` only.

**Exact shape wanted** (mirror of the `%` fact; note the extra
`a < 2^64` hypothesis — `a / b ≤ a` is the range argument, where `%`
got its range from `< b`):
```lean
theorem SliceMem.applyStrictOp_div_u64 {σ : ExecState} {a b : Nat}
    (ha : a < 2 ^ 64) (hb : 0 < b) (hb64 : b < 2 ^ 64) :
    applyStrictOp σ .div [.int (a : Int) .uint64, .int (b : Int) .uint64]
      = .ok (.int ((a / b : Nat) : Int) .uint64, σ)
```
**Consumers:** rle (landed, local witness in
`proofs/GoLeanProofs/Examples/RunLength/HarnessR.lean`); any future
`/`-using family or subject.

**Cost here:** ~20 lines.

### [lane B] KIT GAP — append/slice-growth vocabulary (THE example's find)

**What the kit could not carry:** `SliceMem` has NO appendSlice
vocabulary at all — no executable fact for either arm of
`applyStmtOp (.appendSlice elem)`, no backing-builder closed form, no
capacity-envelope idiom. This example proved locally
(`proofs/GoLeanProofs/Examples/RunLength/HarnessR.lean`):

1. `lookup_set_ne_local` — `Heap.set` at one key preserves every other
   key's lookup. (Tiny; the kit's set/lookup laws are all
   append-shaped, none is the plain set/lookup commuting fact.)
2. `buildAppendBackingValue_one` — the backing-builder closed form at
   `oldValues = #[]`, one appended element, SYMBOLIC capacity `c ≥ 1`:
   result `= .ok (.array ⟨(v :: replicate (c-1) 0).map …⟩)`.
3. `applyStmtOp_append_spill1` — the SPILL arm at this example's site
   shape (append one element onto a cap-0 slice), with the consumed
   capacity choice surfaced as an EXISTENTIAL:
   `∃ cap ch', 1 ≤ cap ∧ cap ≤ 32 ∧ applyStmtOp … = .ok ({σ with heap :=
   set (set heap ⟨nextAddr⟩ backing) target handle, nextAddr+1}, ch')`.

**Exact shape a kit closure would need** (generalized from the above):
```lean
-- the general backing builder closed form
theorem SliceMem.buildAppendBackingValue_u64 {σ} {old new : List Int}
    (hold : ∀ v ∈ old, 0 ≤ v ∧ v < 2 ^ 64)
    (hnew : ∀ v ∈ new, 0 ≤ v ∧ v < 2 ^ 64) {c : Nat}
    (hc : old.length + new.length ≤ c) :
    buildAppendBackingValue σ tU64 (mapU old) (mapU new) c
      = .ok (.array ⟨((old ++ new) ++ List.replicate (c - …) 0).map …⟩)
-- the spill arm, general lengths, envelope existential
theorem SliceMem.applyStmtOp_append_spill {σ ta} {s e : SliceValue} … :
    ∃ cap ch', newLen ≤ cap ∧ cap ≤ appendSpillUpper s.cap newLen ∧ …
-- the IN-PLACE arm (this example never needed it; n ∈ [4,8] does)
theorem SliceMem.applyStmtOp_append_inPlace …
```
**Consumers:** rle (landed), stack/queue (chartered — both `append`),
any future growable-slice subject.

**Cost here:** ~200 lines (the three lemmas plus their simp-fights over
`forIn` desugaring).

### [lane B] KIT GAP — choice-dependent allocation layout (the n ∈ [4,8] blocker)

**What the kit could not carry — and what BLOCKED the domain, not just
cost lines:** after a spill whose capacity came from the choice
stream, whether the NEXT append spills (allocates) or extends in place
is choice-dependent, so every later heap address shifts by the number
of spills so far. Raw `with_unfolding_all rfl` segments need literal
addresses; a proof over all streams therefore needs one segment set
per spill history (3 layouts at rle's second new-run event, 5 at its
third, multiplied across the two output slices), which is out of reach
by hand. Two kit shapes would each close it:

1. **An address-shift frame lemma**: if
   `stepFnIter k σ c ch = .ok (c', σ', ch')` and every address the
   segment touches is `< B`, then the same run holds with all
   addresses `≥ B` shifted by `d` (state, config, continuation). This
   is a simulation over the step function — heavy, but it makes ONE
   literal-address segment set serve every spill history.
2. **A conditioned micro-step library**: per-`Config`-shape stepFn
   lemmas (exec-seqn, exec-init/alloc at symbolic `nextAddr`,
   evalE-var via env+lookup hypotheses, …) so an iteration can be
   walked at symbolic addresses without `rfl`. ~15 lemmas plus a
   chaining idiom; turns ~60 raw steps per iteration into ~60 lemma
   applications.

**Consumers:** rle's `n ∈ [4, 8]` regime (the recorded honest gap);
stack/queue past their first reallocation; ANY subject whose
allocation count depends on data or choices.

**Cost here:** the domain restriction `n ≤ 3` (disclosed in the
headline, the root docstring, and the Audit shard) — this one is the
example's most valuable output.

### FINDING FOR THE CAMPAIGN'S INPUT STREAM (not a G1 item)

**`append`'s spill arm CONSUMES the nondeterminism-choice stream.**
`applyStmtOp (.appendSlice)` allocates a fresh backing when
`newLen > cap` and draws the new capacity from `Choices` inside an
envelope `[newLen, max 32 (2·growth)]` (`appendSpillUpper`). That makes
`rle` the **third** gallery example where `∀ ch` does real work, and the

here the quantifier ranges over Go's latitude in *how much capacity a
growing slice gets*. Two consequences worth the operator's attention:

1. It is a genuine, correctly-modelled degree of freedom (the Go spec
   promises only "a new, sufficiently large underlying array"), so this
   is the envelope working as designed — the theorem holds at every
   capacity in it.
2. It means slice growth is a latitude point whose ENVELOPE WIDTH has
   now been exercised by a proof rather than only by the differential.
   Whether `appendSpillUpper`'s specific upper bound is the right width
   is a fidelity question for the G3 dossier lane, not for this one.
   Recorded here as an input, with no machine change and no proposal.
