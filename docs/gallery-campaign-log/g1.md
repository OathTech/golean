### The example

**Go** (`Corpus/coverage/exec/examples/histogram/main.go`): `histogram`
builds a `map[uint64]uint64` of counts over a `[]uint64`, reads the
count of a queried key (`counts[q]` — Go's zero value on an absent
key), then counts the map's entries with a VARIABLE-FREE
`for range counts {}`. Harness `histogram_harness_r(n, seed, q)` is the
S3 RELATIONAL style: setup family `v[i] = seed + i%3`, a copy loop into
a fixed-cap `[8]uint64`, then `histogram(v, q)` — the values AND both
summaries returned as data.

- **JC (observable choice):** both summaries returned, not one — the
  queried count exercises the map INDEX READ and `distinct` exercises
  the enveloped `for range`. The charter asked that the observable
  range over the map so the `∀ch` teaching point is real; `distinct`
  does, and its spec (`distinctCount`) is a function of the returned
  values alone. Principle: the harness ruling (returned data over a
  verdict) + the charter's order-invariance requirement.
- **JC (variable-free range):** `for range counts {}` rather than
  wordcount's `for _, c := range counts`. It is the honest lowering of
  "count the entries", and it makes the machine side markedly cheaper —
  `bindIterVars` with no binders allocates NOTHING, so the range loop is
  state-stable. Principle: velocity, where honesty is unaffected (the
  Go is what a Go programmer would write).

### The proof, in one paragraph

Entry → setup loop (57 steps/iteration, the P5 schema) → copy loop (53)
→ ONE program-consulting `enterFrame` → the subject's prologue (51) →
the counting loop (84/iteration, `Histogram/CountLoop.lean`) →
`hits := counts[q]` (the map READ, `MapMem.applyStrictOp_mapGet`, Go's
zero value on an absent key) → `distinct := 0` → the map-range loop (16
steps/iteration, one choice consumed, ZERO allocation) → the epilogue.
Two pure bridges carry the answers: `cnt_countsList'` (the map's count
at a key IS that key's number of occurrences) and `countsList_length`
(the histogram has exactly as many entries as the list has distinct
values). The second is what makes the enveloped loop's answer readable.

### The proof, in one paragraph

Entry → the `mod == 0` guard (21 steps) → the `mod == 1` guard (9) →
`result := 1` and the `base % mod` apply (25 + 1) → the `$forFirst`
block to the loop head (18) → first-pass dispatch (25) → **the loop**,
by induction on the exponent's BIT BUDGET → exit (40). One iteration is
92 steps when `exp` is odd and 72 when it is even; the two branches
share a 44-step tail (`pm_iter_tail`) covering the squaring, the
halving and the next dispatch. Six `applyStrictOp` steps per iteration
are data-dependent and each is discharged by a conditioned executable
fact. Two pure bridges carry the answer: `powLoop` (the loop's own
recursion) and `powLoop_eq` (that it computes `(r · bᵉ) mod m`), so the
headline states MATHEMATICS while the induction states the loop.

### Judgment calls (this unit)

- **JC (the spec is mathematics, not the loop):** the postcondition is
  `if mod = 0 then 0 else base ^ exp % mod`, with `powLoop` confined to
  the proof layer behind `powLoop_eq`. Principle: claim ≤ theorem cuts
  both ways — a spec that merely re-describes the program is a claim
  that says nothing, and the gallery exists to be READ. Cost: the
  modular-arithmetic bridge (~45 lines).
- **JC (the domain is the SOURCE's no-wrap condition, verbatim):** the
  hypothesis is `(mod − 1) * (mod − 1) < 2 ^ 64`, which is exactly the
  condition the Go comment states, rather than a rounder `mod ≤ 2^32`.
  Principle: honesty beats elegance — the theorem's domain and the
  program's documented domain are then the same sentence, and the wrap
  region is excluded in the open rather than by a convenient constant.
- **JC (all three guard paths in ONE theorem):** `mod = 0` and
  `mod = 1` are proved as machine paths rather than excluded by
  hypothesis, so the entry covers the whole documented domain below the
  wrap threshold. Cost: two extra raw segments and two short
  compositions (~35 lines). `mod = 1` needed no case in the SPEC,
  because `base ^ exp % 1 = 0` — the guard and the mathematics agree,
  and that is worth a reader's attention.
- **JC (bit-budget induction ⇒ a CONSTANT bound):** the loop induction
  is `∀ d, exp < 2 ^ d → k ≤ 92·d + 40`, instantiated at `d = 64`,
  rather than an induction on `exp` giving a bound linear in `exp`.
  Principle: bound tightness is a delegated judgment call, and `6027`
  is both tighter and far more legible than any `c·exp` would be.
- **JC (probe-first, not guess-first — the flagship's reflex, paid

### The example

**Go** (`Corpus/coverage/exec/examples/palin/main.go`): `isPalindrome`
walks two indices inward — `i` up from `0`, `j` down from `len(s)-1` —
returning `0` at the FIRST mismatched pair and `1` if the walk meets in
the middle. Harness `palin_harness_r(n, seed)` is the S3 RELATIONAL
style: setup family `s[i] = seed + i%2`, a copy loop into a fixed-cap
`[8]uint64`, then `isPalindrome(s)` — the checked array AND the verdict
returned as data.

### THE FINDING THIS UNIT CONTRIBUTES: the two-exit loop

Every subject loop in the shipped gallery leaves ONE way, so every
shipped loop lemma ends at a loop head and the run assembly chains the
exit afterwards. `isPalindrome` leaves TWO ways that are not symmetric:
the loop's exit test (walk met in the middle → `return 1`) and a
`return 0` from INSIDE the body (first mismatch). The consequence is
structural, not cosmetic:

* `ph_loopP` runs all the way to the DRIVER TERMINAL rather than to a
  loop head, and its content is that BOTH exits deliver the same
  observable — `palinSpec l` in `$res1` either way.
* The loop's own `i`/`j` cells are EXISTENTIALLY QUANTIFIED in its
  conclusion (`∃ k iv jv, …`), because the two exits stop at different
  indices and nothing the harness returns depends on which. That is
  the honest way to say "the loop-local state is not observable"
  without inventing a normal form for it.
* The two exit segments (`ph_bailP` 70 steps, `ph_outP` 49 steps) are
  proven separately and the induction picks between them.

`twosum` (early return from a nested loop), `bubble` (the `!swapped`
early exit) and `rle` all have this shape too, which is why it is
written up here rather than left inside the example.

- **JC (loop shape):** run the subject induction to the terminal and
  existentially quantify the loop-local cells, rather than normalizing
  the two exits to a common `i`/`j`. Principle: honesty beats elegance
  — a normal form would be a fiction about where the program stopped,
  and the observable genuinely does not depend on it.
- **JC (statement strength):** the headline states `verdict =
  palinSpec pre` (a functional equation) and ships
  `palin_verdict_iff` as the FIRST-ORDER readout (`v = 1 ↔
  pre.reverse = pre`) rather than making the iff the headline.
  Principle: the statement-TCB doctrine — headline theorems ship
  first-order readout corollaries; the reader gets the form they can
  check without unfolding a definition, and the proof keeps the form
  it composes with.
- **JC (spec shape):** `palinSpec xs = if xs.reverse = xs then 1 else 0`
  — no index arithmetic in the STATEMENT at all; the half-scan
  characterisation the Go actually decides is a THEOREM
  (`palin_iff_half`), not a definition. Principle: the gallery's whole
  purpose is that the claim be readable without the algorithm.

### First-action probe findings (the string semantics, established
### before any Lean was written)

- A Go string is a pure VALUE (`GoValue.string`, a `GoString` byte
  array) — no backing cell, no handle, no allocation on `+=`. So
  `len(s)`, `s[i]`, string `+`, and every string store reduce
  DEFINITIONALLY inside `with_unfolding_all rfl` segments. This
  example has ZERO `storeTarget`/`Heap.lookup` conditioning; its only
  conditioned steps are the three `enterFrame`s and three pure
  strict-op facts (`stringFromRune` at ASCII, string `indexGet`, the
  kit's `%`).
- `string(rune(c))` lowers to `.stringFromRune (.convert (.int
  .int32) …)` and the machine implements the FULL UTF-8 encoder
  (`GoString.fromCodePoint`), surrogate range included. A byte `≥ 128`
  read back through `string(rune(s[i]))` would return TWO bytes —
  faithful Go — which is why the reverse loop's invariant carries
  `∀ b ∈ pre, b.toNat < 128` (`strFamily_ascii`) and why no theorem
  claims byte-reversal for non-ASCII strings.
- `s[i]` on a string is `stringByteGet` on the VALUE (yields `.int ↑b
  .uint8`); `len` is `.int ↑bytes.size .int`; `+` is `GoString.append`
  (array append, no normalize step); string stores normalize by
  constructor match (identity).
- `buildStr`'s byte is `97 + ((seed+i) mod 2^64) mod 26` — the inner
  wrap is real (Go uint64 `+` wraps BEFORE `%26`), and the family
  definition keeps it rather than pretending `%` distributes.

### THE LANE'S HEADLINE FINDING — `append` is a nondeterminism site, and
### the first brief was WRONG about it

The lane owner's first briefs told the `stack` and `queue` workers that
`∀ ch` was VACUOUS for their examples and handed them a concrete table
of backing addresses and capacities to unroll against. **Both claims
were false, and they were caught by probing rather than by reading.**

What the machine actually does (probe, `stack` harness):

| ch | total steps | `nextAddr` | choices consumed | final `s` header |
|---|---|---|---|---|
| `[]` | 1282 | 77 | 0 | base 48, len 8, cap 8 |
| `[0]*6` | 1282 | 77 | 2 | base 48, len 8, cap 8 |
| `[299]*6` | 1282 | **76** | **1** | base **19**, len 8, cap **15** |
| `[3]*6` | 1282 | 77 | 2 | base **69**, len 8, cap **17** |

- A SPILLING `append` consumes ONE choice; an append that fits its
  capacity consumes none. So even the NUMBER of choices a run consumes
  is choice-dependent — an early large capacity suppresses a later
  spill.
- The realized capacity is an ENVELOPE, not a number:
  `[newLen, max 32 (2 · appendGrowthCap oldCap newLen)]`
  (`GoLean/GoCore/Ops.lean`), because gc's realized capacity depends on
  element size through size-class rounding and the compiler's 32-byte
  stack buffer — mechanisms an element-size-free growth formula cannot
  see. The corpus row `slices/append-spill-size-class` pins this at
  `stage=membership` with 300 enumerated members.
- **The step count is choice-INVARIANT** (1282 at every stream): an
  `append` is ONE machine step whether it spills or not. This is what
  lets a single fuel bound cover every stream.
- The heap layout is NOT choice-invariant: backing address, capacity and
  allocation front all move.

Cross-checked against the reference implementation: the default-stream
capacity sequence for `[]uint64` is `0 → 4 → 8 → 16`, which a `go run`
probe reproduces EXACTLY. So the machine's default point is gc's, and
the envelope around it is the honest latitude, not a divergence.

- **JC (correct the workers mid-flight rather than let it land):** the
  correction went out the moment the probe came back, before either
  worker had written a push-loop segment. Principle: the two bounds —
