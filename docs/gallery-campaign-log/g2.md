### E3 — THE FIDELITY ARGUMENT (2026-08-15, unit G2.E3 — written BEFORE the implementation)

The charter's E3 clause: "evaluation-order fidelity argued against the
spec and pinned by corpus cases before landing". This section is that
argument, committed with the guardrail rows and before any frontend
code changes. The two spec texts that govern (spec.golang.org, "Logical
operators" and "Order of evaluation"):

> Logical operators apply to boolean values and yield a result of the
> same type as the operands. **The right operand is evaluated
> conditionally.**
>
> `&&    conditional AND    p && q  is  "if p then q else false"`
> `||    conditional OR     p || q  is  "if p then true else q"`

> ...when evaluating the operands of an expression, assignment, or
> return statement, all function calls, method calls, receive
> operations, **and binary logical operations** are evaluated in
> lexical left-to-right order.

**The design.** GoCore has no call expressions (calls are statements),
so the existing A-normal-form discipline hoists a call in expression
position to a temp bound immediately before the enclosing statement.
The RHS of `&&`/`||` cannot take that hoist — it would run a call the
spec runs only conditionally — which is exactly the standing quarantine
(`emit.go` `emitBinary`, reason "call/allocation in short-circuit
operand (would change evaluation order)"). The normalization instead
emits the spec's own rewrite AS STATEMENTS. For `x && y` with an
effectful `y` (`||` analogously with the negated test):

```
<x's own hoists>              -- LHS effects, unconditional, first
$cN := <x>                    -- the LHS value binds, exactly once
if $cN { <y hoists>; $cN = <y> }
<the expression lowers to the temp read $cN>
```

The RHS is emitted once into its own accumulator; if that accumulator
comes back EMPTY (pure RHS), the inline `Expr.and`/`Expr.or` lowering
is kept byte-identical to today — the normalization fires only where
the quarantine fires today, so no lowering outside the currently-red
set can change. The spec's `"if p then q else false"` **is** this
conditional: `$cN` false ⇒ the body is skipped ⇒ the result is the
banked `false`; `$cN` true ⇒ the body evaluates `y`'s effects in
lexical order and delivers `y`. Frontend-only, in the `NativeToIR`
quarantine-discipline sense: existing GoCore statements (`assign`,
`if`, `block`), no new node, no decoder change.

**What could go wrong, and how the design excludes each:**

1. **Double evaluation** (an operand's effects run twice): `<x>` and
   `<y>` each appear at exactly ONE position in the emitted statements
   (the temp bind; the conditional body); every later use reads the
   temp. The accumulator capture is a *placement* decision over a
   single emission — nothing is emitted twice (the BUG-047 class,
   speculative re-emission, cannot arise because there is no fallback
   re-emit path).
2. **Eager right operand** (RHS runs when the LHS already decided):
   every `y`-derived statement — its call hoists AND the value
   delivery — is inside the conditional body, guarded by exactly the
   spec's condition (`$cN` for `&&`, `!$cN` for `||`). There is no
   `y`-derived statement outside it.
3. **Order swap** (RHS effects before LHS effects): the accumulator is
   append-ordered and emission is left-to-right — `x`'s hoists, then
   the temp bind of `x`'s value, then the conditional carrying `y`.
   The decoder splices hoists in order at every site.
4. **Introduced or reordered effects**: the added machinery is a fresh
   temp declaration, temp reads, and an `if` — all effect-free. Temp
   names are `$`-prefixed, unspellable in Go source, so no capture.
5. **Loop conditions** (the stein shape, `for isEven(a) && isEven(b)`):
   the machinery rides the existing `condPre` mechanism, which
   re-splices condition hoists before EACH test inside the loop — so
   per-iteration re-evaluation of both operands, with per-iteration
   short-circuit, is inherited from a mechanism the corpus already
   pins, not re-implemented. Same story for `else if` (else-branch
   splice) and switch case expressions (per-test splice): the
   machinery lands wherever a call hoist lands today.
6. **Nesting** (`f(a) && (g(b) || h(c))`): the inner operation
   normalizes into the OUTER's RHS accumulator, so its whole machinery
   sits inside the outer conditional body — evaluated only when the
   outer LHS admits it, in lexical order. Each level wraps its own.

**Panic-timing altitude, stated honestly:** binding `$cN := <x>` moves
the LHS's *pure residue* (e.g. an index panic) to the statement's
ordered-hoist prefix. That is the SAME treatment hoisted calls already
give their inline argument residues, and the binary logical operation
is a member of the same spec-ordered class as calls (the "Order of
evaluation" sentence above), so this introduces no new latitude class —
the pure-RHS inline path (unchanged) and the `comparisons/short-circuit/*`
panic-timing pins (8 rows, all PASS, MUST NOT drift) keep pinning the
existing story.

**The boundary (fail-closed remainder), scoped honestly:** the
normalization admits into the conditional body exactly what the single
`hoist()` temp-binding path produces — plain (single-value) call
temps and kin. Every OTHER quarantined effect keeps the standing
per-site refusal verbatim, because `hoistForbidden` stays SET during
the RHS emission and only `hoist()` (plus the normalization's own
wrap) gains the admission: **channel receives** (`hoistChanRecv` —
concurrency-envelope shapes are not E3's scope and have no guardrail
rows here), **make/new/append/copy**, **slice and map literals**,
**`&composite` allocations**, **interface method values**, and
**multi-value splats** (unreachable in a bool operand anyway). Each
still classifies `unsupported` with its existing reason. Widening any
of these later owes its own guardrail rows first.

**The guardrail rows (committed RED with this section, before the
implementation):** `bools/short-circuit-effects/` — five subjects over
a package-level effect counter/trace, pinning exactly the risk classes
above, each row's expected value computed from the spec rewrite and

* `scCount` (counter): eager RHS evaluation changes the observable
  count — risk 2; double evaluation changes it too — risk 1.
* `scOrder` (`||` digit trace): left-to-right AND exactly-when-needed —
  risks 2, 3 (an order swap yields a different digit string).
* `scNested` (`f(a) && (g(b) || h(c))` digit trace): risk 6.
* `scLoop` (`&&` guard on a `for`): per-iteration re-evaluation and
  per-iteration short-circuit — risk 5.
* `scAssign` (expression position, not a condition): the temp-read
  lowering in a plain assignment.

Plus the three pre-existing red guardrails (`bools/short-circuit-and`,
`bools/short-circuit-or`, `bools/short-circuit-call-operand` — closure

### E2 — `fmt` subset in the frontend — **NON-PULL (reasoned)**

No harness-style example pulls `fmt`, and the reason is structural rather
than incidental: **observation in the settled harness styles is via
RETURN VALUES, not printing.** S2 returns a scalar, S3 returns the
pre-state, post-state and summaries as pure values; the machine observes
what the function returns. `fmt` appears in every corpus `main.go` only
inside `func main()`, which is never a corpus subject.

The one style that would have pulled it, S4 RELATIONAL-STRING
(pre/post encoded as `fmt.Sprint`-shaped strings), is the branch the
harness scoping study explored and REJECTED
(`docs/2026-08-14_harness-style-scoping.md` §9, "S4 NOT recommended
anywhere") — its only advantage, unbounded data, is delivered better by
the choice-input annotation, and it alone thickens the below-statement
layer and doubles the encoder surface.

So E2's non-pull is a consequence of a ruling already on the record, not
a gap in this wave's coverage. A non-pull finding IS a valid G2 shape
record: the charter says pulled-not-pushed, and building `fmt` because it
was on a list would be the push.

## Findings recorded as INPUTS (the byproduct stream)

- **E2 and E4 share one mechanism.** Both quarantines are the same
  frontend refusal — `selector call <Fn> is not a method value` — fired
  by `fmt.Sprint` and `strings.Repeat` alike. The extension list treated
  them as two; the machine has one boundary. Any future stdlib work
  should be scoped to the mechanism, not per-package.
- **The machine is AHEAD of the driver on uint64 arguments.** E1 is
  entirely a test-harness limitation. Worth noting for the two-bounds
  doctrine: the differential's lower bound is currently narrower than the
  machine's expressible range for reasons that have nothing to do with
  semantics.
- **The gallery's driver-limitation sentences were STALE the moment E1
  landed, and are now corrected** (`docs/verified-examples.md`).
  `reverse`'s Ground paragraph said "no oracle row reaches the `uint64`
  wrap region" and `minmax`'s said its wrap behaviour was checked "on the
  machine only, with no `go run` oracle in the loop" — the weaker-evidence
  admission that made E1 worth building. Both now state the region is
  oracle-witnessed and name the rows; `isort` and `wordcount` gained their
  new rows in the same pass (counts 11→14, 13→16, 11→13, 11→14
  respectively). A gallery claim that outlives the limitation it confesses
  is exactly the staleness the entries are supposed to prevent, so the
  correction ships in E1's own commit.
- **A latent driver/machine asymmetry, checked and left alone: leading
  zeros.** `strconv.ParseInt("0123", 10, 64)` is `123`, but the Go SOURCE
  literal `uint64(0123)` is OCTAL `83` — so a leading-zero argument would
  mean different things to the validator and to the generated harness. It
  is not exploitable today: no corpus row has one (checked across every
  `cases.tsv`), and the MACHINE side refuses such an argument outright
  (`golean … --arg-int 0123` → `offset 1: expected end of input`), so the
  case would fail loudly rather than diverge silently. Recorded rather
  than fixed, because E1's brief was a smallest-diff change to oracle
  infrastructure; the natural guard is one clause in
  `scripts/coverage-manifest`'s existing `^-?[0-9]+$` arg regex.
- **Fail-closed lowering is legible in the golden pins.** `stein`'s repr
  records the quarantine SHAPE (`Ty.unsupported` / `Stmt.unsupported`
  with the reason inline), not merely its effect. That makes a golden pin
  a usable record of what the frontend refuses, which was not a designed
  property of the pins but is a good one.
