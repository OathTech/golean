## THE PULL-LIST

### E1 — differential driver `--arg` past int64 — **PULLED**

**Consumer:** `dotprod` (`Corpus/coverage/exec/examples/dotprod/`),
landed this wave, 14 rows all PASS. Designated because it is the
overflow-rich example: four of its rows exercise a genuine mod-2^64
wrap, probe-verified per product —

* `four-wrap` `3*(2^63-1)` → `2^63` exactly
* `one-wrap` `(2^63-1)^2` → `1`
* `harness-r-wrap-max` seed = int64 max: products wrap at 7 of 8 indices
* `harness-r-wrap-62` seed = 2^62: products wrap at 5 of 8 indices

Additionally, EVERY array example in the wave carries a wrap-region row
at the largest value expressible today (`9223372036854775807`), so the
extension has a broad acceptance set, not a single consumer.

**The gap is ONE-SIDED, and that is what makes it cheap.** The machine
already handles the full uint64 range:

```
$ golean native-json-run … --arg-int 18446744073709551615
{"schema":"golean-observation-v1","status":"ok","values":[{"kind":"uint64","tag":"int","value":18446744073709551615}]}
```

The block is the GO-ORACLE harness generator, which parses arguments as
SIGNED int64 — `tools/coverageharness/main.go:159`,
`strconv.ParseInt(part, 10, 64)` — and rejects anything larger, verbatim:

```
invalid integer argument "18446744073709551615": strconv.ParseInt: parsing "18446744073709551615": value out of range
```

(`scripts/diff-coverage` itself only validates `^-?[0-9]+$` before
forwarding to the machine, so it is not the constraint.)

**What E1 owes when it is built:** the charter also requires renaming the
`harness-wrapping` row id with its re-pin. Guardrail rows for the region
above int64 max CANNOT be written before the extension — the oracle
cannot accept them — so E1 is the one extension whose guardrails land
*with* it rather than before it. Recorded here rather than glossed: the
guardrails-first rule is satisfied instead by the landed wrap rows below
the boundary, which pin the wrapping SEMANTICS the extension must not
disturb.

### E3 — calls in short-circuit operands — **PULLED**

**Consumer:** `stein` (`Corpus/coverage/exec/examples/stein/`), landed
this wave, **9 rows, ALL RED at stage `frontend-export`** — the recorded
quarantine, a visible expected gap.

Binary GCD written the way Go programmers write it needs
`for isEven(a) && isEven(b)`. The calls were deliberately NOT hoisted:
hoisting produces a green example of a program nobody writes and leaves
E3's target behaviour unpinned at exactly the moment the extension gets
built.

The refusal is fail-closed, per-declaration, and legible in the pinned
lowering itself (`baselines/golden/stein-lowered.repr`): `steinGCD`
lowers to `Stmt.unsupported` carrying the reason verbatim and its
parameters to `Ty.unsupported`, while `stein_harness` lowers fully and
calls into that stub.

Independent Go-side verification, so the red is unambiguously the tool's:
`steinGCD` agrees with the `gcd` example's Euclid on all seven argument
pairs and on a 100,000-pair xorshift sweep — zero mismatches.

**What E3 owes when it is built:** evaluation-order fidelity argued
against the SPEC TEXT (the hoisting must preserve Go's short-circuit
guarantee — the hoisted call must not run when the left operand already
decides the result); the nine rows flipping to PASS is the acceptance
test; and `baselines/golden/stein-lowered.repr` DRIFTS deliberately, in
the same commit, with its reason.

### E4 — string-construct coverage — **NON-PULL (probed, not assumed)**

The charter scoped E4 to "string-construct coverage **as pulled by
reserve-list examples**". Probed against the real pipeline: the reserve
examples pull NOTHING. Every string construct that string reverse and
string palindrome need already classifies `"status":"ok"` (table above),
and strings cross the observation boundary as
`{"tag":"string","bytes":[...]}` — contents, not a handle.

The finding is not a paper one: **`strrev` landed this wave, 12 rows all
PASS, E4-INDEPENDENT** — including the empty string
(`{"bytes":[],"tag":"string"}`), a max-seed row, and both the reverse and
the palindrome subjects.

**E4's actual boundary is not string constructs at all.** It is the
standard-library CALL:

```
strings.Repeat → "normalizing frontend-quarantined: selector call Repeat is not a method value"
```

which is the SAME mechanism as E2's `fmt.Sprint`, not a string-language
gap. So E4 as chartered has no consumer; a *stdlib-selector-call*
extension would, and it would subsume E2. Recorded as an INPUT below
rather than silently re-scoped — re-scoping an extension to keep a count
is exactly the push the charter forbids.

### E2 — `fmt` subset in the frontend — **NON-PULL (reasoned)**

No harness-style example pulls `fmt`, and the reason is structural rather
than incidental: **observation in the settled harness styles is via
RETURN VALUES, not printing.** S2 returns a scalar, S3 returns the
pre-state, post-state and summaries as pure values; the machine observes
what the function returns. `fmt` appears in every corpus `main.go` only
inside `func main()`, which is never a corpus subject.

The one style that would have pulled it, S4 RELATIONAL-STRING
(pre/post encoded as `fmt.Sprint`-shaped strings), is the branch the
harness scoping study explored and REJECTED
(`docs/2026-08-14_harness-style-scoping.md` §9, "S4 NOT recommended
anywhere") — its only advantage, unbounded data, is delivered better by
the choice-input annotation, and it alone thickens the below-statement
layer and doubles the encoder surface.

So E2's non-pull is a consequence of a ruling already on the record, not
a gap in this wave's coverage. A non-pull finding IS a valid G2 shape
record: the charter says pulled-not-pushed, and building `fmt` because it
was on a list would be the push.

| extension | verdict | consumer | evidence |
|---|---|---|---|
| **E1** | **PULLED** | `dotprod` (14 rows PASS, 4 wrap rows) | one-sided driver gap, `coverageharness/main.go:159`, verbatim rejection |
| **E3** | **PULLED** | `stein` (9 rows RED at `frontend-export`) | verbatim quarantine, pinned in the golden repr |
| E4 | **NON-PULL** | — (`strrev` landed without it, 12 rows PASS) | every needed construct `ok`; real boundary is the stdlib selector call |
| E2 | **NON-PULL** | — | observation is by return, not printing; S4 already rejected |

**HONEST STATUS: the G1 candidate set pulls TWO of the four named
extensions, not three.** This is a finding, not a shortfall to be papered
over, and it is exactly what "pulled not pushed" is supposed to surface:
two of the four extensions were named before the pipeline was probed, and
the probes say the machine already does what they were meant to unlock.

Consequences for the campaign, for the operator to weigh (NOT resolved
here — extension scope is a charter question):

1. **Build E1 and E3.** Both have landed consumers waiting and neither is
   speculative.
2. **A third pulled extension must be FOUND, not chosen.** The honest
   candidate the probes actually surfaced is **stdlib selector calls**
   (`pkg.Fn(...)`), which subsumes E2 and E4's real boundary into one
   mechanism with a genuine fail-closed remainder. It has no landed
   consumer yet — a `strings`- or `fmt`-using example would have to be
   chartered first, and the harness styles argue against needing one.
3. Alternatively the campaign accepts TWO extensions with the reasoned
   non-pulls recorded, and G2's "≥ 3" is amended at the same level it was
   set. That is the operator's call.

## Findings recorded as INPUTS (the byproduct stream)

- **E2 and E4 share one mechanism.** Both quarantines are the same
  frontend refusal — `selector call <Fn> is not a method value` — fired
  by `fmt.Sprint` and `strings.Repeat` alike. The extension list treated
  them as two; the machine has one boundary. Any future stdlib work
  should be scoped to the mechanism, not per-package.
- **The machine is AHEAD of the driver on uint64 arguments.** E1 is
  entirely a test-harness limitation. Worth noting for the two-bounds
  doctrine: the differential's lower bound is currently narrower than the
  machine's expressible range for reasons that have nothing to do with
  semantics.
- **Fail-closed lowering is legible in the golden pins.** `stein`'s repr
  records the quarantine SHAPE (`Ty.unsupported` / `Stmt.unsupported`
  with the reason inline), not merely its effect. That makes a golden pin
  a usable record of what the frontend refuses, which was not a designed
  property of the pins but is a good one.
