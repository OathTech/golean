### E3 — THE FIDELITY ARGUMENT (2026-08-15, unit G2.E3 — written BEFORE the implementation)

The charter's E3 clause: "evaluation-order fidelity argued against the
spec and pinned by corpus cases before landing". This section is that
argument, committed with the guardrail rows and before any frontend
code changes. The two spec texts that govern (spec.golang.org, "Logical
operators" and "Order of evaluation"):

> Logical operators apply to boolean values and yield a result of the
> same type as the operands. **The right operand is evaluated
> conditionally.**
>
> `&&    conditional AND    p && q  is  "if p then q else false"`
> `||    conditional OR     p || q  is  "if p then true else q"`

> ...when evaluating the operands of an expression, assignment, or
> return statement, all function calls, method calls, receive
> operations, **and binary logical operations** are evaluated in
> lexical left-to-right order.

**The design.** GoCore has no call expressions (calls are statements),
so the existing A-normal-form discipline hoists a call in expression
position to a temp bound immediately before the enclosing statement.
The RHS of `&&`/`||` cannot take that hoist — it would run a call the
spec runs only conditionally — which is exactly the standing quarantine
(`emit.go` `emitBinary`, reason "call/allocation in short-circuit
operand (would change evaluation order)"). The normalization instead
emits the spec's own rewrite AS STATEMENTS. For `x && y` with an
effectful `y` (`||` analogously with the negated test):

```
<x's own hoists>              -- LHS effects, unconditional, first
$cN := <x>                    -- the LHS value binds, exactly once
if $cN { <y hoists>; $cN = <y> }
<the expression lowers to the temp read $cN>
```

The RHS is emitted once into its own accumulator; if that accumulator
comes back EMPTY (pure RHS), the inline `Expr.and`/`Expr.or` lowering
is kept byte-identical to today — the normalization fires only where
the quarantine fires today, so no lowering outside the currently-red
set can change. The spec's `"if p then q else false"` **is** this
conditional: `$cN` false ⇒ the body is skipped ⇒ the result is the
banked `false`; `$cN` true ⇒ the body evaluates `y`'s effects in
lexical order and delivers `y`. Frontend-only, in the `NativeToIR`
quarantine-discipline sense: existing GoCore statements (`assign`,
`if`, `block`), no new node, no decoder change.

**What could go wrong, and how the design excludes each:**

1. **Double evaluation** (an operand's effects run twice): `<x>` and
   `<y>` each appear at exactly ONE position in the emitted statements
   (the temp bind; the conditional body); every later use reads the
   temp. The accumulator capture is a *placement* decision over a
   single emission — nothing is emitted twice (the BUG-047 class,
   speculative re-emission, cannot arise because there is no fallback
   re-emit path).
2. **Eager right operand** (RHS runs when the LHS already decided):
   every `y`-derived statement — its call hoists AND the value
   delivery — is inside the conditional body, guarded by exactly the
   spec's condition (`$cN` for `&&`, `!$cN` for `||`). There is no
   `y`-derived statement outside it.
3. **Order swap** (RHS effects before LHS effects): the accumulator is
   append-ordered and emission is left-to-right — `x`'s hoists, then
   the temp bind of `x`'s value, then the conditional carrying `y`.
   The decoder splices hoists in order at every site.
4. **Introduced or reordered effects**: the added machinery is a fresh
   temp declaration, temp reads, and an `if` — all effect-free. Temp
   names are `$`-prefixed, unspellable in Go source, so no capture.
5. **Loop conditions** (the stein shape, `for isEven(a) && isEven(b)`):
   the machinery rides the existing `condPre` mechanism, which
   re-splices condition hoists before EACH test inside the loop — so
   per-iteration re-evaluation of both operands, with per-iteration
   short-circuit, is inherited from a mechanism the corpus already
   pins, not re-implemented. Same story for `else if` (else-branch
   splice) and switch case expressions (per-test splice): the
   machinery lands wherever a call hoist lands today.
6. **Nesting** (`f(a) && (g(b) || h(c))`): the inner operation
   normalizes into the OUTER's RHS accumulator, so its whole machinery
   sits inside the outer conditional body — evaluated only when the
   outer LHS admits it, in lexical order. Each level wraps its own.

**Panic-timing altitude, stated honestly:** binding `$cN := <x>` moves
the LHS's *pure residue* (e.g. an index panic) to the statement's
ordered-hoist prefix. That is the SAME treatment hoisted calls already
give their inline argument residues, and the binary logical operation
is a member of the same spec-ordered class as calls (the "Order of
evaluation" sentence above), so this introduces no new latitude class —
the pure-RHS inline path (unchanged) and the `comparisons/short-circuit/*`
panic-timing pins (8 rows, all PASS, MUST NOT drift) keep pinning the
existing story.

**The boundary (fail-closed remainder), scoped honestly:** the
normalization admits into the conditional body exactly what the single
`hoist()` temp-binding path produces — plain (single-value) call
temps and kin. Every OTHER quarantined effect keeps the standing
per-site refusal verbatim, because `hoistForbidden` stays SET during
the RHS emission and only `hoist()` (plus the normalization's own
wrap) gains the admission: **channel receives** (`hoistChanRecv` —
concurrency-envelope shapes are not E3's scope and have no guardrail
rows here), **make/new/append/copy**, **slice and map literals**,
**`&composite` allocations**, **interface method values**, and
**multi-value splats** (unreachable in a bool operand anyway). Each
still classifies `unsupported` with its existing reason. Widening any
of these later owes its own guardrail rows first.

**The guardrail rows (committed RED with this section, before the
implementation):** `bools/short-circuit-effects/` — five subjects over
a package-level effect counter/trace, pinning exactly the risk classes
above, each row's expected value computed from the spec rewrite and

* `scCount` (counter): eager RHS evaluation changes the observable
  count — risk 2; double evaluation changes it too — risk 1.
* `scOrder` (`||` digit trace): left-to-right AND exactly-when-needed —
  risks 2, 3 (an order swap yields a different digit string).
* `scNested` (`f(a) && (g(b) || h(c))` digit trace): risk 6.
* `scLoop` (`&&` guard on a `for`): per-iteration re-evaluation and
  per-iteration short-circuit — risk 5.
* `scAssign` (expression position, not a condition): the temp-read
  lowering in a plain assignment.

Plus the three pre-existing red guardrails (`bools/short-circuit-and`,
`bools/short-circuit-or`, `bools/short-circuit-call-operand` — closure

### E5 — THE FIDELITY ARGUMENT (2026-08-15, unit G2.E5 — written BEFORE the implementation)

**The design.** The machine has no stdlib and must not grow one: a
stdlib function modeled as a GoCore node would put library behaviour
inside the semantic core, where only Go LANGUAGE semantics belongs. An
E5 shim is instead **frontend-maintained lowering code in the
quarantine zone**: a Go-SOURCE function, written in the already-modeled
subset, that the frontend injects into the user's package (as a
synthetic file, before type-check) whenever an allowlisted call shape
`strings.Fields(x)` is present, rewriting exactly those call sites into
ordinary static calls to the injected function. Consequences, each
load-bearing:

* **No GoCore change, no wire change, no decoder change.** The shim
  lowers through the SAME pipeline as user code and lands in the
  emitted program as one more function; the golden pin of any consumer
  records its lowered body — the refusal boundary stays legible.
* **The allowlist is named and everything else keeps refusing
  verbatim.** One entry: `strings` → `Fields`. `strings.Repeat`,
  `fmt.Sprint`, and every other selector call keep the standing
  per-declaration quarantine, byte-identical (probe-verified after the
  build, below). Widening the allowlist later owes its own guardrail
  rows and its own argument, one function at a time.
* **Collisions fail closed.** The shim's reserved names
  (`goleanShimStringsFields`) are collision-checked against the user's
  package scope at injection; a user declaration of that name refuses
  loudly rather than silently merging.

**THE VALIDATION INSIGHT — the corpus is the shim's conformance
suite.** `go run` executes the REAL `strings.Fields`; the machine
executes the SHIM. Every differential row whose control flow passes
through a shimmed call is therefore a direct oracle test of shim
fidelity — not an indirect one: any semantic daylight between the shim
and the stdlib is a `values`-level mismatch on that row. This is the
same two-bounds shape as everywhere else (a row witnesses membership,
never the envelope), but for a PURE, DETERMINISTIC function the
envelope is a single behaviour per input, so here the rows bite
unusually hard: one row per behaviour class pins that class outright.
The 8 `strings/fields-conformance/*` rows are chosen to cover the
behaviour classes below, and the `wordfreq` rows re-cross the shim on
every built input.

**The shim's semantics vs the stdlib's documented behavior.** The
contract (Go stdlib doc, `strings.Fields`): "Fields splits the string
s around each instance of one or more consecutive white space
characters, as defined by unicode.IsSpace, returning a slice of the
substrings of s or an empty slice if s contains only white space."
The shim implements the FULL class, as a byte-level scan with no rune
decoding: `unicode.IsSpace` is White_Space=yes, a small closed set,
and its members' UTF-8 encodings are finitely enumerable —

* 1 byte: `09 0A 0B 0C 0D 20` (`\t \n \v \f \r` and space);
* 2 bytes: `C2 85` (U+0085 NEL), `C2 A0` (U+00A0 NBSP);
* 3 bytes: `E1 9A 80` (U+1680), `E2 80 80`…`E2 80 8A` (U+2000–200A),
  `E2 80 A8`/`A9` (U+2028/2029), `E2 80 AF` (U+202F), `E2 81 9F`
  (U+205F), `E3 80 80` (U+3000).

**Why a byte scan equals the stdlib's rune scan.** Real Fields (slow
path) decodes runes and tests `unicode.IsSpace`; the shim
pattern-matches the encodings above at each position, consuming the
separator's width on a hit and one byte otherwise. Equality holds
because (a) every pattern starts with a byte in `09–20`/`C2`/`E1`/
`E2`/`E3`, and none of those is a UTF-8 continuation byte, so a
pattern can never fire from inside a preceding valid rune; (b) on
valid UTF-8 the scan is position-for-position the rune scan (a
non-space rune's bytes contain no pattern start that completes); (c)
on INVALID UTF-8, real Go decodes `RuneError` with width 1 — never
white space — and the shim likewise treats any byte that completes no
pattern as content; a TRUNCATED space prefix (`E2 80` at end of
string) completes no pattern and stays content on both sides. Two
behaviour notes at the boundary of observability: the empty-vs-nil
identity of the returned slice is UNOBSERVABLE in the value fragment
(corpus subjects observe fields via `len`/index/join, and a
zero-field result behaves identically either way on that surface);
and the shim pins TODAY'S White_Space table — if a future Unicode
revision changed it (it is stability-listed; it has not changed since
Unicode 4.1), the conformance rows would go visibly red under the
newer toolchain, which is the re-envelope obligation firing exactly
as designed.

- **A latent driver/machine asymmetry, checked and left alone: leading

## POST-AUTONOMY AUDIT (2026-08-16) — the closure quarantine LEAK, and a flag for records pass 2

Recorded here because it lives at exactly the boundary E3 built and E5
extended, and because the *records* half of this finding is not finished.

**The finding (audit R2A-F2).** `emitFuncLit`
(`tools/nativefrontend/emit.go:5276`) saved and restored **ten** pieces
of emitter state around a function literal's body — `captureParam`,
`hoisted`, `curFuncName`, `fnHasRecv`, `curResults`, `branchLabels`,
`gotoLabels`, `gotoSeg`, `gotoPC`, `gotoLoop` (`emit.go:5338–5343`,
restored at `:5357–5360`) — but NOT `hoistForbidden` / `scHoistOK`.
[Count corrected 2026-08-16, fix round #2: this said "nine", as did
`9ee5f1f3`'s commit message, but the very list both of them give has ten
entries — the miscount was of its own sentence. With the fix's two flags
the emitter now saves twelve.]
So a func literal appearing inside a short-circuit RHS emitted its OWN
statements under `hoistForbidden = "short-circuit operand"`, and any
`make` / `append` / composite inside the literal was refused at the
boundary.

**Why it is a bug and not a conservative choice.** The restriction says
"do not hoist a call/allocation OUT of this expression, because that
moves it across a short-circuit". A literal's body is emitted into its
own lifted function: its statements never enter the enclosing statement
stream, so there is nothing to hoist out and no evaluation order to
change. The refusal was an OVER-refusal — the fail-closed-classification
class the green gates structurally cannot see, because a wrongly
`unsupported` case is indistinguishable from an expected coverage gap.

**The fix, guardrails-first, in two commits.** 11 rows in
`Corpus/coverage/exec/bools/short-circuit-funclit` landed RED first (7
leak witnesses at stage `frontend-export` with the verbatim reason
`make in short-circuit operand`, plus 4 controls carrying the identical
literal body outside any short-circuit, PASS); then the two-flag
save/restore; then exactly those 7 flipped, controls unmoved, full
`scripts/ci --diff` and baseline re-pin in the same commit (1841 cases,
1743 PASS, 98 FAIL — the FAIL set back to its standing size).

**Fail-closed remainder, probe-verified BEFORE and AFTER and
byte-identical**, nine shapes each placed directly in a short-circuit
RHS: channel receive, `make`, `new`, `append`, `copy`, slice literal,
map literal, `&composite`, interface method value. Same wire messages,
character for character.
