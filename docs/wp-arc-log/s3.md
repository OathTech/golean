# THE NAMING CONVENTION, as normalized

Descriptive first, prescriptive second: §§1–3 are what the library
ALREADY does, written down and checked against every public name;
where a rule and a name disagreed the near-miss is recorded in §5,
not silently renamed.

## 1. Module shape — the standard block order

Every kit module's docstring now has, in this order:

1. `# <title>` + provenance (arc/slice/date, what it was lifted from);
2. the module's own scope/design prose (unchanged);
3. `## PUBLIC API — the sealed interface` — numbered groups **indexed
   by PROOF SITUATION** ("you are trying to X"), in FILE order, every
   public declaration in exactly one group;
4. `**Internal**` — the `private` list, or the explicit words
   "Internal: none";
5. `**Naming note**` where the module has a convention worth stating
   or a recorded exception;
6. `**The API discipline**` — five numbered rules: (1) untrusted
   method / no kit name in a headline closure, (2) consumers depend
   on STATEMENTS not proofs, (3) additions follow the §12
   active-abstraction loop, (4) pin coverage in `Audit/Kit.lean`,
   (5) **storm/signature discipline = StepKit rules 1–5, CITED**;
7. `## WHAT LIVES WHERE` — this module in one sentence, then one
   bullet per sibling giving the BOUNDARY (not just the name), then
   the `docs/kit-guide.md` section names this module feeds.

In-file section headers are `/-! ## API group N — <the group's own
words> -/`, with `### API group N, continued` where a group
legitimately spans two places in the file.

**The storm rules live in exactly one place.** `StepKit`'s
`## THE FIVE RULES` is that place (rules 1–3 the segment-shape rules,
4–5 the footprint signature disciplines); every other module cites
them and adds at most one line saying which one bites there. Before
this slice, MapLoops paraphrased rules 1–3 in its own words.

## 2. Declaration names

### 2.1 The seven families

| family | shape | examples |
|---|---|---|
| executable fact | `<executable fn>_<operand or result shape>`, the fn at its shortest UNAMBIGUOUS spelling in the namespace | `applyStrictOp_indexGet_slice`, `applyStrictOp_len_string`, `storeTarget_slice_u64`, `applyStmtOp_append1_inplace`, `mapAssignValue_toEntries`, `snapshot_toEntries` |
| one-step glue | `stepFn_<what the step does>` | `stepFn_call_enter`, `stepFn_seqn_splice`, `stepFn_pick_bind` |
| multi-step glue | `stepFnIter_<what>` — and it lives in `FuelMeasure`, because it counts steps | `stepFnIter_chain`, `stepFnIter_call_span`, `stepFnIter_iterate` |
| heap algebra | `<operation>_<shape>`, reading the statement head outward | `lookup_append_left`, `set_cons_ne`, `set_comm`, `lookup_singleton_self` |
| predicate | CamelCase; see the DOT RULE below | `DeadFrom`, `FreshFrom`, `CompletesIn`, `Sorted`, `CellFixed`, `EntryLayout` |
| data family | a `def`, then `<family>_length` / `_range` / `_succ` / `_set` / `_getD` (+ a `Z`-suffixed `Int`-valued range variant where a consumer needs it); `getD_<family>_<case>` where the READ is the head symbol | `familyMod`, `familyZ`, `familyF`, `familyOf`, `takePad`, `prefixPad`, `padZ`, `swapList`; `familyModZ_range`; `getD_swapList_fst` |

### 2.2 THE DOT RULE (predicates)

A lemma that **consumes** the predicate is dot-namespaced, so
`h.push` works: `DeadFrom.push`, `FreshFrom.set`, `CompletesIn.mono`,
`CellFixed.of_locFree`.
A lemma that **produces** one from non-predicate premises is
snake-cased: `completesIn_comp`, `completesIn_measure_loop`,
`completesIn_next_stop`, `terminates_of_completesIn`.

Checked against every predicate lemma in the seven modules at
`5cd08332`: the rule is exactly descriptive. The `CompletesIn.mono`
vs `completesIn_comp` split that reads as an inconsistency IS this
rule; it was simply unwritten. **Zero aliases needed.**

## 3. The vocabulary family, and its one exception

`<kind>Cells` / `<kind>Val` holds for slices and maps.
`StringMem.gs` is the recorded EXCEPTION: a Go string is unbacked, so
there is no heap half to name, and `gs` produces the `GoString`
CONTENT that a `.string` value wraps — not a `GoValue` handle. The
exception is now stated in StringMem's docstring rather than left to
be rediscovered. See §5.3 for why it was not aliased.

## 5. Near-misses considered and REJECTED

**5.1 `stepFn_store_step`, `stepFn_makeSlice_u64_step`** — the
trailing `_step` is redundant (15 of the 17 `stepFn_*` lemmas lack
it). REJECTED: 204 and 20 landed use sites respectively
(`grep -rn '\bstepFn_store_step\b' proofs --include='*.lean' | grep
-v '.lake' | wc -l` at `61d55f5a`). An alias adds a second name
without retiring the first, and a `@[deprecated]` attribute would
emit 224 warnings into a gate whose core build must be WARNING-free.
Recorded instead as the rule for NEW names: `stepFn_<arm>`, no
`_step`. *JC: legacy spelling with >200 consumers stays; the
convention binds new names — honesty about the irregularity beats
churn that pretends to remove it.*

**5.2 `MapMem.snapshot_toEntries`, `MapMem.scan_generic`** — they
abbreviate their executable functions (`mapRangeSnapshotEntries`; the
`mapEntryIndex?` scan). REJECTED as ALREADY CONFORMING: the family
rule is the shortest UNAMBIGUOUS spelling in the namespace, and both
are unambiguous. *JC: sharpened the rule to say "unambiguous" rather
than renaming two lemmas to match a rule stated too rigidly.*

**5.3 `StringMem.gs`** — does not match `<kind>Cells`/`<kind>Val`.
REJECTED: it is neither (see §3), and the spelling is load-bearing —
398 occurrences across `proofs/`, and every example keeps its OWN
definitionally-equal `gs` def because headline statements spell it
and no kit name may enter a headline closure (§12b), which is what
makes the examples' copies zero-proof delegations. *JC: a documented
exception beats a rename that would break the delegation pattern the
exception exists to serve.*

**5.4 `CompletesIn.mono` vs `completesIn_comp`/`_measure_loop`/
`_next_stop`** — apparent dot-vs-snake inconsistency inside one
predicate's lemma set. REJECTED: the DOT RULE (§2.2) explains the
split exactly, and the same split holds in `StepKit` and
`Frame/Threshold`. The convention was already followed; only the
statement of it was missing. *JC: wrote the rule down instead of
"fixing" names that were already right.*

**5.5 `SliceMem.swapList_length` vs `getD_swapList_fst`** — apparent
subject-first vs operation-first inconsistency. REJECTED: both read
the STATEMENT head outward (`(swapList …).length` vs
`getD (swapList …) i`), i.e. the same rule.
