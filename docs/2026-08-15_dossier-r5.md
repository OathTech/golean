# Dossier R5 — float division by zero: panic or not (narrowed to no-panic)

G3 register item 13. Inventory §R5. Proposal only — batched for user
ruling.

## 1. The latitude

Whether float/complex division by zero raises a run-time panic is
implementation-specific. Machine: IEEE ±Inf/NaN, never a panic
(Machine.lean:270–275, the float arm dispatching before the integer
zero check). The envelope is {no-panic-IEEE, panic}.

## 2. Evidence

### SPEC (go1.26.5, §Floating-point operators)

> "The result of a floating-point or complex division by zero is not
> specified beyond the IEEE 754 standard; whether a run-time panic
> occurs is implementation-specific."

Note the two-part grant: the VALUE is IEEE-constrained (±Inf/NaN are
forced up to IEEE's own latitude), only the PANIC-OR-NOT is free.

### GC probes (`docs/evidence/2026-08-15-dossier-r5/`, verbatim)

    1.0/z = +Inf, -1.0/z = -Inf, 1.0/nz = -Inf, z/z = NaN,
    f32/z32 = +Inf, reached end: no panic

All sign/NaN shapes and float32: IEEE specials, no panic — the
machine's point (also pinned by the corpus case
`floats/division-specials`). Contrast probe: integer division by zero
panics (`integer divide by zero`) — that one is spec-MANDATED, not
latitude.

### Corpus / de-facto spec

This is the strongest de-facto singleton in the register: deployed Go
relies pervasively on non-panicking float division (NaN/Inf
propagation through statistics, graphics, JSON number edge paths —
`math.Inf`/`math.IsNaN` exist to consume these values). An
implementation that panicked would break an enormous body of running
code; under the de-facto-spec evidence class the plausible envelope
has effectively collapsed to no-panic even though the text grants
more. No conforming-but-panicking implementation is known.

### XIMPL / ARCH

NOT-OBTAINED (no toolchains/web). gccgo and tinygo both realize
IEEE no-panic (local knowledge, UNVERIFIED). ARCH: the sentence has
carried the panic latitude unchanged since Go 1; no known
implementation ever exercised it (local knowledge, UNVERIFIED).

## 3. Proposed disposition

**PERMANENT-RECORD narrowing (no-panic singleton); revisit only on
cross-implementation evidence of a panicking realization.**

- ARGUMENT: the de-facto argument above is as strong as this evidence
  class gets — the panic member is spec-permitted but plausibly
  unrealizable in a viable implementation (it would break the
  ecosystem). Widening to admit a panic outcome would weaken every
  float-division theorem (an ∃-panic disjunct) for a member with no
  witness anywhere, ever — the exact "modeling behavior never
  observed and never plausible" cost the pragmatic-subset doctrine
  (R2's precedent) avoids.
- COUNTER-ARGUMENT: the doctrine's weakest-machine ideal says the
  spec text IS the upper bound and it names the panic member;
  permanence forecloses it on de-facto reasoning alone. REBUTTAL: the
  doctrine ranks evidence classes and explicitly empowers the
  deployed-corpus argument ("an implementation cannot plausibly break
  behaviors that a large body of running code depends on"); this is
  its textbook application. The record (this dossier) keeps the
  revisit condition explicit rather than silent.
- WHAT WOULD CHANGE THE ANSWER: any conforming implementation
  observed panicking (would instantly reopen as a two-point
  envelope); a Go spec change deleting the sentence (would make
  no-panic FORCED and close the entry entirely — worth checking at
  toolchain bumps).

## 4. Evidence gaps

- XIMPL: NOT-OBTAINED (gccgo/tinygo claims marked UNVERIFIED).
- Complex division by zero: unprobed (complex is outside the
  machine's modeled surface today); recorded so the entry re-opens
  with complex support.
