# Spec divergence ledger

Established 2026-08-17 (spec-truth campaign P4, mechanism 4.3 —
`docs/2026-08-17_spec-and-community-truth-campaign.md`). One entry per
known or discovered gap between the spec text, gc behavior, and/or the
machine. The mechanical feed is the archaeology census
(`docs/spec-archaeology/*.tsv`, regenerated by
`scripts/mine-spec-archaeology` from the pinned `deps/go`); entries
here are the CURATED, verified subset. Latitude *realizations* (where
spec permits many behaviors and machine/gc pick points) live in the
latitude inventory, not here — this ledger records faults,
ambiguities, and prior-art records with a fault-shaped question.

## Schema (per campaign §4.3 + the P1 amendments)

Fields per entry: **id** · **kind** ∈ {`spec-ambiguity`, `spec-bug`,
`gc-bug`, `gc-divergence-tolerated`, `ours`, `prior-art`} (the last
added per the FG note — model-vs-implementation records that fit no
fault triple) · **how found** ∈ {mining, differential, spec-re-read,
probe, community-seed, prior-art} (SpecTec RQ2 lesson: detection
channel predicts fix cost) · **sources** (spec#/mem# anchors, commits,
issues) · the Cerberus question format: a **sharp question**, a
**minimal program** where one exists, **per-implementation data**, and
for `gc-divergence-tolerated` the **usage-vs-implementation** split
(what code relies on vs what gc does) · **stance** · **bound
affected** · **status** (incl. upstream).

Discipline notes, recorded up front:
- **Kind-attribution at N=1 is ARGUED, never voted** (ESMeta note
  §3.3): with gc as the only oracle, every verdict needs spec anchor +
  probe + reasoning; JEST's cheap majority vote needs the
  cross-implementation lane (P5 decision).
- **The SpecError triage question** (ESMeta note): a differential red
  whose triage shows the SPEC text (not our code) incoherent or silent
  at that point is a `spec-ambiguity` candidate, not only a bug-in-us.
- Expected mix (ESMeta note): Go's prose spec expresses defects mostly
  as *ambiguity*; expect more `spec-ambiguity` than `spec-bug`.
- Upstream expectations (CH2O note §4): filings buy standing and
  answers; normative text moves slowly even for the best cases.
  Per-filing sign-off by Mike, always.

## Entries

### L-001 — close built-in: spec required what gc never enforced — `spec-bug` (FIXED upstream)

- How found: mining (census row 2025-12-02, anchor `spec#Close`).
- Sources: spec#Close; golang/go#74034; fix commit `1a64db3a4b3f`
  ("remove restriction on channel element types for close built-in
  (bug fix)").
- Sharp question: for `close(ch)` with `ch`'s type a type parameter,
  must all channel types in the type set share one element type?
- Data: spec said yes ("channels with the same element type"); gc
  never enforced it since generics shipped (1.18) — the commit body
  says so explicitly — and the requirement was "not important for
  correctness or required by the implementation". Text amended
  2025-12-02 to "must be channels".
- Stance: archetype of the de-facto-wins resolution inside Go's
  single-owner model: a 3.5-year-old spec-vs-gc divergence, closed by
  editing the SPEC. Upper-bound lesson: at generics arcs, the pinned
  spec text may over-constrain relative to settled gc behavior —
  check the spec history of the governing clause before enforcing a
  restriction gc doesn't.
- Bound affected: upper (a machine enforcing the old text would
  refuse programs conforming-by-amendment). Status: closed upstream;
  the fix IS an ancestor of the go1.26.5 pin (`git merge-base
  --is-ancestor 1a64db3a4b3f <pin>` — established by ancestry, not
  date comparison; argument corrected at the P4 audit). No action
  owed.

### L-002 — FG dispatch vs gc dispatch — `prior-art`

- How found: prior-art (FG/memory-model note §1.3/§4.1).
- Sources: FG paper §3.4 Fig. 14 (`r-call`, call-time lookup) + §2.1
  efficient-implementation prose; Sulzmann/Wehr APLAS'21 Theorem 1 +
  the 2022 extension.
- Content: FG resolves methods at call time from the receiver's
  dynamic type; gc fixes the itab at interface-construction time.
  Proven observationally equivalent ON THE FG FRAGMENT ONLY
  (termination, divergence, panic); method sets/pointer receivers,
  embedding, nil interfaces are all outside the theorem.
- Stance: GoCore's `TypeId`-keyed dispatch is FG-shaped; the
  differential pins it today. Goes live at any generics/
  dispatch-representation arc. Bound: neither, today.

### L-003 — FGG is not shipped generics — `prior-art`

- How found: prior-art (same note §1.4).
- Content: FGG formalizes the 2019 contracts-era draft; Go 1.18+ type
  sets, unions, `~`, and constraint inference have no FGG counterpart.
- Stance: at the generics arc, FGG supplies the typing skeleton,
  monomorphisability theory (nomono), and the bisimulation obligation
  (Thm 5.4, dummy-method trap); the PINNED SPEC supplies the language.

### L-004 — sequenced-before delegates to the spec's evaluation order — informational

- How found: spec-re-read (FG/memory-model note §2.1/§4.1).

- Content: the memory model's per-goroutine order is a PARTIAL order
  exactly where the spec's evaluation order is open — E2–E5's latitude
  (and E12's, the entry added on the spec-p2 lane landing alongside;
  dangling-id caught at the P4 audit) is memory-model latitude too,
  under concurrency.
- Stance: recorded at E1's cross-link (P2 retrofit); matters the day

### L-005 — select has no memory-model text — absence record

### L-006 — go_mem gained normative text with no anchor or version-line change — informational (tripwire lesson)

- How found: audit of the P1 notes (R2's F-1), verified twice.
- Sources: `deps/go` commit `977e23a707` (2023-07-31), mem#restrictions.
- Content: 13 insertions / 2 deletions — ~9 lines of new normative
  per-sub-value any-order text plus rewordings (precision per the P4
  audit) — while the "Version of June 6, 2022" line and the full

- Stance: neither anchor existence nor the version line is a

  alongside this ledger, not present on this branch's own tree
