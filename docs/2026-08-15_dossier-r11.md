# Dossier R11 — sync misuse fatal class (pinned to gc's throw realization)

G3 register item 17. Inventory §R11 (register extension #7's family);
sync design §8. Borderline-IN judgment (g3.md): observable from a
single goroutine. Proposal only — batched for user ruling.

## 1. The latitude

DOCS: "It is a run-time error if m is not locked on entry to Unlock"
— the CLASS of that error is underdetermined (recoverable panic?
unrecoverable fatal?). gc realizes an unrecoverable runtime throw.
Machine: `GoError.fatal` with gc's fixed strings; recorded narrowing:
the fatal observation carries the fatal alone, dropping gc's
pending-panic line when raised during unwinding (sync design §8).
go-of-nil-func remains REFUSED, not migrated to the class.

## 2. Evidence

### DOCS (sync package)

> "It is a run-time error if m is not locked on entry to Unlock."

(And RWMutex's twin sentences.) "Run-time error" names neither
`runtime.Error`-panic nor fatal — the class is the latitude.

### GC probes (`docs/evidence/2026-08-15-dossier-r11/`, verbatim)

- `Mutex.Unlock` unlocked: `fatal error: sync: unlock of unlocked
  mutex`, in-binary exit 2.
- `RWMutex.RUnlock` unlocked: `fatal error: sync: RUnlock of
  unlocked RWMutex`, exit 2.
- STRONGER-THAN-RECORDED datum: the deferred function in the probe
  produced NO output — a runtime throw does not run deferred
  functions AT ALL (the recover machinery is never reached), not
  merely "recover does not catch". The machine's fatal terminal
  (which short-circuits unwinding) models this correctly; the
  dossier records the sharper phrasing for the site docs.
- Contrast within the same package (R8's probe): WaitGroup misuse is
  a RECOVERABLE PLAIN-STRING panic — gc realizes both classes,
  per-API, so the pin must be per-operation (and is).

### Corpus / de-facto spec

Production code relies on sync misuse being LOUD (deadlock/misuse
bugs surface as crashes in CI); no deployed code recovers from
unlock-of-unlocked (impossible — that is the point of the throw).
De-facto pressure holds the fatal class in place: making it
recoverable would let buggy programs limp on with corrupted lock
state, which the runtime team explicitly refuses (local knowledge,
UNVERIFIED).

### ARCH / XIMPL

ARCH: in pre-1.8-era Go, sync misuse raised recoverable panics;
the migration to unrecoverable `throw` was deliberate (local
knowledge, UNVERIFIED — the inventory's "historical gc change class"
note). XIMPL: NOT-OBTAINED.

## 3. Proposed disposition

**PERMANENT-PIN at gc's current point (fatal class + exact strings),
version-tracked by the fatal cases** — the inventory's posture,
affirmed; plus one site-doc sharpening: record that the throw skips
deferred functions entirely (probed), so the machine's
short-circuit terminal is the CORRECT model, not an approximation.

- ARGUMENT: the envelope {recoverable panic, unrecoverable fatal} is
  real (ARCH witnesses the other point historically), but no CURRENT
  implementation realizes recoverable, and a claim consumer wanting
  "recover catches sync misuse" would be verifying a bug. The pin's
  strings and class are already differentially tracked.
- COUNTER-ARGUMENT: the historical point shows the class can move
  again. REBUTTAL: version-tracking pins exist for exactly this; a
  future gc migration fires them and the entry re-opens with a real
  second member.
- WHAT WOULD CHANGE THE ANSWER: a gc release changing the class
  (pins fire); XIMPL divergence; the pending-panic-line narrowing
  (fatal-during-unwinding) gaining a consumer — it is the one
  recorded sub-point where our observation drops a line gc prints,
  and a strict-lane abort-output case there would go red (recorded,
  unprobed here — the shape needs a panic in flight, which the
  single-goroutine probes cannot compose simply).
