# Dossier R14 — constant arithmetic precision ((d) UNKNOWN, delegated — now analyzed)

G3 register item 20 (= U-3). Inventory §R14. Proposal only — batched
for user ruling.

## 1. The latitude

§Constants sets MINIMUM implementation requirements (≥ 256-bit
integers, ≥ 256-bit mantissa / 16-bit exponent floats) and mandates:
error if an integer constant cannot be represented precisely; error
on float overflow; ROUND to nearest representable on float precision
limits. Everything above the minimum is latitude — in ACCEPTANCE
(which programs compile) and, via the float-rounding rule, in VALUES.
The frontend delegates all constant evaluation to go/types, so
machine and oracle share one realization.

## 2. Evidence

### SPEC (go1.26.5, §Constants, verbatim)

> "Implementation restriction: Although numeric constants have
> arbitrary precision in the language, a compiler may implement them
> using an internal representation with limited precision. That said,
> every implementation must: Represent integer constants with at
> least 256 bits. Represent floating-point constants ... with a
> mantissa of at least 256 bits and a signed binary exponent of at
> least 16 bits. Give an error if unable to represent an integer
> constant precisely. Give an error if unable to represent a
> floating-point or complex constant due to overflow. Round to the
> nearest representable constant if unable to represent a
> floating-point or complex constant due to limits on precision."

### GC probes (`docs/evidence/2026-08-15-dossier-r14/`, verbatim)

- 500-bit intermediates fold exactly (`x = 1024`) — above the
  256-bit minimum, so a minimal implementation may REJECT what gc
  accepts.
- **gc's integer limit is exactly 512 bits** (bisected: `1<<511`
  accepted, `1<<512` → `constant shift overflow`; 1000-bit product →
  `constant multiplication overflow`). gc is NOT
  arbitrary-precision: a wider implementation would ACCEPT programs
  gc rejects. The acceptance latitude cuts BOTH ways around gc's
  point.
- Shift counts have a separate cap (`invalid shift count 5000`).
- **FINDING — the inventory's "no runtime observable" is REFUTED**:
  `const tiny = 1.0 + 1e-100; tiny != 1.0` prints `true` under gc
  (exact rational constant arithmetic) but a conforming
  256-bit-mantissa implementation MUST round `tiny` to `1.0`
  (the spec's rounding rule), printing `false`. Constant precision
  is a VALUE latitude with runtime-observable divergence between
  conforming implementations — not acceptance-only.

### Alignment fact (VERIFIED through the actual frontend)

The frontend delegates to go/types, and the limits are IDENTICAL,
probed through `tools/nativefrontend` itself
(`docs/evidence/2026-08-15-dossier-r14/frontend-limit.txt`): the
1<<500 program exports (exit 0); the 1<<512 program is rejected with
the SAME message gc gives (`type-check: ... constant shift
overflow`). Machine and oracle sit on the same realized point by
construction AND by measurement — there is no machine-vs-oracle
divergence to guard, only a transfer scope vs OTHER conforming
implementations.

### Corpus / de-facto spec

Real code's constants live far below 256 bits (crypto constants are
the outliers and stay under 512); float constants beyond float64
precision appear mainly in generated math tables, where authors
already expect rounding. De-facto pressure keeps all realistic
programs inside EVERY conforming implementation's envelope.

## 3. Proposed disposition

**CLOSE the (d) UNKNOWN as: DELEGATED-PIN to go/types' realized
point (shared with the oracle by construction), with a PERMANENT
SCOPE NOTE covering both discovered edges:** (i) acceptance —
programs with 257–512-bit constant intermediates are accepted here
but rejectable by minimal conforming implementations, and programs
needing > 512 bits are rejected here but acceptable elsewhere;
(ii) values — constant float comparisons finer than 256 mantissa
bits (the `tiny != 1.0` shape) do not transfer to minimal conforming
implementations. No machine change; no Choices site (the latitude
lives in the FRONTEND's constant folding, upstream of the machine).

- ARGUMENT: machine ≡ oracle by construction makes a differential
  envelope meaningless here; the honest artifact is the scope note,
  and the probes give it exact numbers (512; the tiny-shape). The
  runtime-observable edge is real but only against hypothetical
  minimal implementations — no realizable oracle exists to
  differentiate against.
- COUNTER-ARGUMENT (negative-lane envelope): the negative lane could
  model "a conforming implementation may reject" as an acceptance
  envelope. REBUTTAL: the negative lane's contract is "go/types
  accepts ⇔ we accept" — an acceptance envelope would weaken its
  decisive signal exactly like R9's message envelopes; the scope
  note is the right instrument.
- WHAT WOULD CHANGE THE ANSWER: an XIMPL lane whose constant
  precision differs (gccgo's is arbitrary-precision GMP — local
  knowledge, UNVERIFIED — which would realize the `tiny` shape's
  other member and the >512-bit acceptance member); a target
  program with >256-bit constant arithmetic.
