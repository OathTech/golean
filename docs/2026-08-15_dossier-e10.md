# Dossier E10 — which `==`-equal map key is retained on overwrite (pinned: always-replace)

G3 register item 8. Inventory §E10; floats design
`docs/2026-08-04_floats-design.md` §4 (arc-final F15). Proposal only —
batched for user ruling.

## 1. The latitude

`m[k] = v` where an `==`-equal key is already stored: the spec is
silent on whether the STORED key object is kept or replaced. The
choice is observable exactly for key kinds where `==`-equal keys are
distinguishable when the stored key is later observed — the recorded
list: float/complex/string/interface/array/struct keys (in-language
observable today: the float signed-zero case via `1/k`; string
retention differs only by backing pointer, unobservable at the
modeled surface). Machine: the NEW key replaces the stored key
(`entries.set! i (key, value)`, Machine.lean:239–243 via
`mapEntryIndex?`, Ops.lean:1638–1647).

## 2. Evidence

### SPEC (go1.26.5)

§Map types requires only that "The comparison operators == and != must
be fully defined for operands of the key type". §Assignments/§Index
expressions define assignment to a map element as setting the VALUE
for the key — nothing about which representative of an `==`-class is
stored. Silence = latitude.

### GC probe (`docs/evidence/2026-08-15-dossier-e10/`, verbatim)

Both overwrite directions on signed zero:

    insert +0, overwrite -0:  1/k = -Inf  v = 2
    insert -0, overwrite +0:  1/k = +Inf  v = 2

gc replaces the stored key in both directions — the machine's
always-replace point, exactly. (The corpus pin
`floats/signed-zero-map-key` is green and version-tracks this; the
probe re-exhibits it first-hand in both directions.)

### The gc-internal nuance (recorded, bears on the envelope's shape)

gc's runtime decides per-type via `needkeyupdate` (floats design §4):
for some key types gc does NOT update the stored key on overwrite.
For those kinds where it doesn't, retention vs replacement is
`==`-indistinguishable anyway (bit-identical keys), so gc's realized
BEHAVIOR coincides with always-replace at the observation surface for
every kind probed. A conforming ORIGINAL-KEY-RETAINING implementation
on float keys would sit outside the pin — the recorded transfer
caveat at the site.

### Corpus / de-facto spec

Code depending on which signed zero a float map key retains is
essentially nonexistent (float map keys are themselves a lint-worthy
rarity; NaN's distinct-entries behavior is the famous trap, and it is
FORCED, not this axis). De-facto pressure: none. The Go runtime's own
choice to update float keys was made for map-internals correctness
(evacuation), not program-visible semantics (local knowledge,
UNVERIFIED).

### XIMPL / ARCH

NOT-OBTAINED. gccgo's map implementation is libgo's — whether it
updates float keys on overwrite is the single datum that would size
the real envelope; probe program ready.

## 3. Proposed disposition

**KEEP THE PIN (always-replace) with its transfer caveat; two-point
retention envelope only when a cross-implementation lane exists** —
the inventory's LOW-cost/LOW-value judgment, affirmed with both
overwrite directions now probed.

- ARGUMENT: the pin matches the oracle at every observable point,
  is version-tracked by a green corpus pin, and the only escape
  (an original-key-retaining implementation on distinguishable kinds)
  has no known witness. The two-point envelope is one arm — cheap —
  but buys zero verification value until an implementation realizing
  the other point exists to differentiate against.
- COUNTER-ARGUMENT: the doctrine's weakest-machine ideal admits the
  retention point now, from spec silence alone; one arm is cheap
  enough to be worth it. REBUTTAL: cheap to ADD is not cheap to CARRY
  (a Choices site at every map store widens every map-bearing
  enumeration for a distinction observable only via signed-zero float
  keys); the caveat carries the honesty at zero runtime cost.
- WHAT WOULD CHANGE THE ANSWER: XIMPL evidence of a retaining
  implementation; or the modeled observation surface gaining a
  string-identity channel (would widen the observable kinds list).

## 4. Evidence gaps

- XIMPL: NOT-OBTAINED (probe ready for gccgo/tinygo).
- Interface/array/struct key retention: unprobed (the observable
  requires an `==`-equal-but-distinguishable pair; for interfaces
  that needs distinct dynamic identities with equal values — a
  fiddlier probe, skipped per the divergence guard; float covers the
  disposition).
