# Dossier E5 — early store across the phase boundary (pinned to the spec-literal point; gc elsewhere)

G3 register item 4. Inventory §E5; BUG-032 final-check amendment
(docs/BUGS.md). Proposal only — batched for user ruling.

## 1. The latitude

For `x, a[i].f = 1, 7/z` (z = 0, recovered): may the store `x = 1`
land BEFORE a phase-1 operand panic (the division)? §Assignments'
two-phase text puts ALL operand/RHS evaluation in phase 1 and ALL
stores in phase 2, but §Order of evaluation orders only
calls/receives/binary-logical — so an implementation that sinks an
early store past the remaining phase-1 work is conforming. The machine
follows the spec-literal order (x stays 0); gc is recorded landing
x = 1 early. NOTE THE ASYMMETRY (inventory §9 flag 3): here OUR point
is the spec-shaped one and gc's is the exotic one — "pinned to gc"
does not describe this axis.

## 2. Evidence

### SPEC (go1.26.5, §Assignments)

> "The assignment proceeds in two phases. First, the operands of index
> expressions and pointer indirections (including implicit pointer
> indirections in selectors) on the left and the expressions on the
> right are all evaluated in the usual order. Second, the assignments
> are carried out in left-to-right order."

The two-phase text reads as store-after-all-evaluation; but because
§Order of evaluation makes only calls/receives/binary-logical
observable-ordered, the panic-vs-store interleaving is unspecified
residue (BUG-032's recorded analysis: "both spec-legal ... §Order of
evaluation orders only calls/receives/binary-logical").

### GC probes (`docs/evidence/2026-08-15-dossier-e5/`, verbatim)

- LOCAL x (the recorded shape): `recovered: runtime error: integer
  divide by zero | x = 1` — the early store, identical under
  `-N -l`. Reproduces the BUG-032 final-check record.
- NEW DATUM — GLOBAL x, same statement: `... | x = 0` — gc realizes
  the SPEC-LITERAL point when the target is package-level (and in the
  swapped-order variant likewise). gc's early store is
  STORAGE-CLASS-DEPENDENT: a liveness/codegen artifact, not a stable
  rule — the same compiler-internal, unpinnable character as E3/E4's
  order picks.

### Machine site

Phase-1-complete-then-store via the tgtOpK → rhsK → storeK spine
(StepFn.lean:459–500; one store per step, Machine.lean:1621–1626).
Distinct mechanism from E3/E4: a fix would hold the STORE back (or
release it early), not linearize panics — BUG-032 records its natural
home as the BUG-025 retirement slice and mandates the membership
treatment for any future pin.

### Corpus / de-facto spec

The observable requires recovering from a panic and then reading a
target of the SAME assignment that panicked — deployed code that does
this and depends on the answer is vanishingly rare (recover-and-reread
of a half-assigned statement is a known anti-pattern; the spec's own
§Assignments example instead pins the PHASE-2 partial-store order,
which is forced and separately implemented). De-facto pressure: none
measurable. gc's own inconsistency between locals and globals is
itself evidence no deployed code can be relying on either answer.

### XIMPL / ARCH

NOT-OBTAINED (no second toolchain, no web). The probe set is ready for
gccgo/tinygo.

## 3. Proposed disposition

**TWO-POINT STORE-TIMING ENVELOPE VIA MEMBERSHIP (admit {x = spec
value, x = early-stored value} on the discriminating shapes); machine
keeps the spec-literal point as canonical. Rides the E3/E4 membership
slice but with its OWN mechanism flag.**

- ARGUMENT: gc is KNOWN outside the machine's point on the local
  shape — an observed-∉-modeled candidate on the strict lane, the
  doctrine's not-at-peace class (same standing as E3/E4). The
  membership treatment admits gc's member; the machine's canonical
  point stays the SPEC-shaped one (the right choice of representative
  — it is the reading a spec-holding reader expects, and the
  storage-class datum shows gc itself realizes it on globals).
- COUNTER-ARGUMENT (keep the pin bare): the observable is a deep
  anti-idiom (recover then read the panicking assignment's own
  target); the standing deviation record may be honest enough.
  REBUTTAL: identical to E3's — a probed gc-elsewhere observation is
  a queued debt by doctrine (§8 correction, adopted); the cost is low
  because the membership machinery is shared with E3/E4.
- COUNTER-ARGUMENT (widen the machine instead — an early-store
  Choices site): gives per-stream determinism. REBUTTAL: the choice
  space is store-sinking schedules (which stores, past which panics —
  storage-class-dependent in gc), not a clean per-site coin; same
  wrong-shape objection the inventory records for R4's fusion axis.
- WHAT WOULD CHANGE THE ANSWER: (i) the E3/E4 slice landing without
  room for a second mechanism (then E5 queues separately — do not
  hold E3/E4 for it); (ii) XIMPL showing no other implementation
  early-stores (would support a permanent-record posture instead);
  (iii) gc unifying its behavior across storage classes.

## 4. Evidence gaps
