# Dossier R3 — `[]byte(s)` conversion capacity (singleton cap = len, gc KNOWN outside)

G3 register item 11. Inventory §R3 (register extension #10; §7 queue
item 4 — "best value-per-cost in the queue"). Proposal only — batched
for user ruling.

## 1. The latitude

§Conversions: the capacity of the slice resulting from
`[]byte(string)` is implementation-specific. Machine: SINGLETON
cap = len, no Choices consumption, transfer caveat at the arm
(Machine.lean:313–333) recording that gc's escaping path realizes
roundupsize(len) — outside the singleton.

## 2. Evidence

### SPEC (go1.26.5, §Conversions to and from a string type)

> "Converting a value of a string type to a slice of bytes type
> yields a non-nil slice whose successive elements are the bytes of
> the string. The capacity of the resulting slice is
> implementation-specific and may be larger than the slice length."

Unbounded-above latitude (≥ len), explicitly granted.

### GC probe (`docs/evidence/2026-08-15-dossier-r3/`, verbatim)

    local    len 5 cap 5
    escaping len 5 cap 5
    local    len 33 cap 33
    escaping len 33 cap 48
    local    len 100 cap 100
    escaping len 100 cap 112

The ESCAPING path sits OUTSIDE the singleton at len 33 (cap 48 =
size class) and len 100 (cap 112) — the recorded caveat reproduced
first-hand, in two size classes. Non-escaping conversions (and small
escaping ones) realize cap = len, so the singleton's point is also a
gc member.

### The class precedent

This is exactly pre-widening BUG-021's class (append-spill: a real
gc behavior outside the model, guarded only by a caveat until the
envelope widening landed with membership pins). The append widening's
mold — envelope [floor, size-class-aware upper], one arm + width
metadata + membership pin for the escaping regime — is proven and
directly reusable; the containment argument at `appendSpillUpper`
(Ops.lean:1829–1854) already covers size-class rounding (worst step
ratio 48/33 < 1.5) for append.

### Corpus / de-facto spec

`[]byte(s)` is ubiquitous; code observing its CAP is rare but real
(capacity-aware buffer reuse after conversion — append-into-converted
patterns). No deployed code can rely on cap = len (gc itself
violates it whenever the conversion escapes and is > small-regime);
de-facto pressure therefore argues the envelope, not the singleton.
A corpus case observing cap of an escaping conversion would go RED
today — the record's own admission.

### XIMPL / ARCH

NOT-OBTAINED (no second toolchain). gccgo/tinygo allocators would
stress the upper end, as with R2.

## 3. Proposed disposition

**WIDEN NOW via the append-spill mold: envelope
[len, roundupsize-style upper], one arm + width metadata + a
membership pin for the escaping regime. This dossier's probe matrix
(two size classes + the exact-cap small regime) seeds the pins.**

- ARGUMENT: gc is measured outside the singleton (three committed
  data points); the mold exists and is proven (BUG-021/R2); cost LOW
  (one arm — the string→[]rune twin stays REFUSED per BUG-020, so
  only the byte arm needs it); the inventory already ranks it best
  value-per-cost (§7 item 4). Under the doctrine, leaving a probed
  known-outside singleton unwidened when the widening is cheap is
  exactly the "at peace with a deviation" posture the §8 correction
  forbids.
- COUNTER-ARGUMENT (defer until a corpus case needs it): no current
  corpus case observes the cap, so nothing is red today; the caveat
  carries the honesty. REBUTTAL: that is survivorship — the case
  does not exist BECAUSE it would be red (the guardrails-first rule
  inverts this: pin the target behavior first). The membership pin
  the widening ships closes the loop properly.
- ENVELOPE-WIDTH argument (the upper end): mirror R2 — a pragmatic
  subset [len, max(32 bytes worth, 2·len)] believed ⊇ gc across
  regimes, never narrowed to one compiler mode, widened deliberately
  if a toolchain leaves the window. The probed points (48/33 ≤ 1.46,
  112/100 = 1.12) sit comfortably inside a 2·len upper.
- WHAT WOULD CHANGE THE ANSWER: a ruling that the append mold's
  width metadata should first be generalized (shared spill-width
  machinery) — then R3 waits for that refactor; or evidence the
  escaping-path detection in a membership pin cannot be made
  deterministic (the pin must FORCE escape — assign to a global, as
  the probe does).

## 4. Evidence gaps

- XIMPL: NOT-OBTAINED (probe ready).
- The exact boundary where gc's escaping cap starts rounding (len 5
  exact vs len 33 rounded — somewhere in between) is unprobed;
  irrelevant to the disposition (the envelope contains both) but
  recorded for the widening slice's pin placement.
