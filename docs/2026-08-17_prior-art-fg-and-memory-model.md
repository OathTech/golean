## 1. FG/FGG — what the calculus actually fixes

### 1.1 What FG is

FG is a tiny call-by-value expression calculus over exactly five expression forms (paper Fig. 11): variables, method calls `e.m(ē)`, structure literals `t_S{ē}`, field selection `e.f`, and type assertions `e.(t)`. A program is a sequence of struct/interface type declarations and method declarations plus `func main() { _ = e }`. Values are fully-evaluated structure literals — nothing else. The two things it fixes precisely:

- **Typing (§3.3, Fig. 13).** Structural subtyping `<:`: a type implements an interface iff its method set includes the interface's specifications (`methods(t_S) ⊇ methods(t_I)`); interface embedding is "assumed expanded out". Method signatures must match invariantly; dispatch is on the receiver only. Type-assertion typing includes the FJ-style "stupid cast" rule `t-stupid` (needed for subject reduction, since reduction replaces interface-typed variables with struct-typed values). Preservation and Progress are proved (Theorems 3.3/3.4), with **panic defined as a stuck failed type assertion**: `e` panics if `e = E[v.(t)]` with `type(v)` not `<: t`. There is no panic *value*, no recover, no propagation machinery — "panic" is a shape of term.

- **Dynamic semantics (§3.4, Fig. 14).** Exactly four reduction rules: `r-field` (project the field from the literal), **`r-call`**, `r-assert` (succeed iff `type(v) <: t`, yielding `v` unchanged), and `r-context` (closure under standard evaluation contexts — deterministic leftmost call-by-value). The load-bearing rule for us is `r-call`:

  ```
  (x : t_S, x̄ : t̄) e = body(type(v), m)
  ─────────────────────────────────────
  v.m(v̄) → e[x := v, x̄ := v̄]
  ```

  Method call is **run-time method lookup**: take the receiver value's dynamic type (`type(v)` reads the constructor tag off the struct literal), look the method body up **at call time** in the program's global declaration list (`body(t_S, m)`, Fig. 12), and β-substitute. No environments, no heap, no closures — substitution into a stateless term.

FGG (§4) extends this with type parameters bounded by interfaces ("type parameters are treated as equivalent to the parameters' bound" in calls and assertions), with one design lesson the paper flags: their first design used nonvariant matching on receiver bounds and had to be relaxed to **covariant** matching to solve the Expression Problem. §5 gives the monomorphisation translation FGG→FG: instance-set collection as a fixpoint of four closures (F/M/I/S), a decidable conservative predicate `nomono` that rejects polymorphic recursion (Fig. 23; Theorems 5.1 Decidability, 5.2 Monomorphisable), name-mangled instance generation with **dummy methods** inserted to preserve *non*-implementation (so `x.(List<bool>)` still fails after monomorphisation — a subtle fail-closed detail worth respecting), and the headline results: Theorem 5.3 (translation preserves typing) and Theorem 5.4 (**bisimulation** between FGG and its monomorphised FG). Their prototype (in Go) dynamically checks preservation/progress and tests the bisimulation square with NEAT-generated programs — a differential discipline recognizably in our family.

### 1.2 What it deliberately omits

The paper is explicit (§8/conclusion): "Featherweight Go is restricted to a tiny subset of Go. We plan a model of other important features such as **assignments, arrays, slices, and packages**, which we will dub Bantamweight Go; and a model of Go's innovative **concurrency mechanism based on goroutines and message passing**, which we will dub Cruiserweight Go." Neither successor calculus appears in the papers we hold (see could-not-verify). Beyond that named list, the omissions that matter for reading FG against GoCore: **no state of any kind** (no heap, no assignment — so no aliasing, no evaluation-order observables; our entire E-series and the granularity ledger have no FG counterpart), **no pointers and hence no method sets** (the value-receiver/pointer-receiver distinction — a central subtlety of real Go dispatch — does not exist), no nil (values are always struct literals; the nil-interface dispatch panic is unrepresentable), no functions as values, no defer/panic-as-value/recover, no primitives (their prototype adds some as extensions), and of course nothing our C-series covers. FG's determinism is total: the calculus has zero latitude points.

### 1.3 The dispatch gap — the claim, pinned down exactly

The dictionary-passing paper states it directly (§1): FG's OOPSLA formalization "specifies static typing rules and a **run-time method lookup semantics** for FG. However, **the actual Go implementation appears to employ a different dynamic semantics**", quoting the FG paper's own prose (§2.1 — corrected from "§3" by audit; the quote occurs exactly once in the paper): *"Go is designed to enable efficient implementation. Structures are laid out in memory as a sequence of fields, while an interface is a pair of a pointer to an underlying structure and a pointer to a dictionary of methods."*

So the gap, stated precisely:

- **FG's semantics**: the method is resolved at **every call**, by looking up `(dynamic type of receiver, method name)` in the global method-declaration table. The binding of interface value to method code happens at call time.
- **gc's implementation** (as described by the FG authors themselves and formalized by Sulzmann/Wehr): the method table is resolved at **interface-construction time** — packing a value into an interface builds/attaches a dictionary (gc's itab: one per (concrete type, interface type) pair), and a call is an indexed lookup into that fixed dictionary. The binding happens at conversion time; the call site never consults the receiver's type again.

These can differ in principle (a conversion-time snapshot vs a call-time lookup is exactly the kind of gap that becomes observable the moment the method table can change or the lookup can fail differently). What the Sulzmann/Wehr pair of papers contributes is the proof that **on the FG fragment they cannot be distinguished**: APLAS 2021 gives a type-directed dictionary-passing translation of FG into an untyped lambda calculus with pattern matching (interface-values = (struct value, dictionary) pairs; a call on interface type = dictionary lookup; structural subtyping struct→interface = dictionary construction; interface→interface = dictionary coercion via destructors) and proves **Theorem 1 (Program Equivalence)** via step-indexed logical relations (step-indexing forced by recursive interfaces and recursive method definitions). The APLAS result held only under a termination assumption; the 2022 semantic-preservation paper (`fg-semantic-preservation.pdf`) removes that limitation with three clauses: source terminates ⇒ target terminates with equivalent value; source **diverges** ⇒ target diverges; source **panics** (failed run-time type check) ⇒ target panics.

The honest scope statement for our ledger: the equivalence is proven **for FG only**. Everything FG omits — pointer-receiver method sets, embedding/promotion, nil interfaces, method values, reflection — is outside the theorem. In full Go those are exactly the places where "when is the method table fixed" has teeth. The theorem is prior art that the two dispatch styles agree on the structural core; it is *not* a license to treat them as interchangeable across the full language.

### 1.4 What FG will settle for golean's generics arc — and what it won't

**Settles (adopt as primary prior art when the arc opens):**
- The **typing skeleton** of structural subtyping with interface-bounded type parameters, and the covariant-receiver-bound lesson (their design iteration is recorded; we should not rediscover it).
- **Monomorphisability as a decidable property**: the nomono predicate and the polymorphic-recursion counterexample (Fig. 10's `Box(Box(a))` nesting) are exactly the shape a monomorphising frontend needs as its fail-closed acceptance check, with a decision procedure and proofs.
- The **bisimulation obligation shape**: if our frontend ever lowers generics by instantiation, Theorem 5.4 is the specification of what that lowering owes, and their dummy-method trick is the recorded solution to the preserve-non-implementation trap (a fail-closed subtlety we would plausibly get wrong first try).
- The **dispatch-equivalence theorem** (Sulzmann/Wehr) as the correctness frame if GoCore's interface dispatch (call-time resolution by `TypeId`, which is FG-shaped) is ever compared against an itab-shaped account of gc.

**Does not settle:**
- **Shipped Go generics are not FGG.** FGG formalizes the 2019 contracts-era draft design (the paper says so — it adopts the July 2019 syntax and notes the 2020 square-bracket revision); the Go 1.18+ spec's type sets, constraint interfaces with unions and `~` approximation elements, and constraint type inference have no FGG counterpart. When the arc opens, the **pinned spec is primary**; FGG is background. (The paper itself predicts the final implementation "will involve a mix of both monomorphisation and runtime representations of types" — see could-not-verify for what gc actually shipped.)
- **Everything stateful.** FGG's substitution semantics says nothing about generics interacting with the heap, assignment, closures, or any latitude point in our inventory. The interesting golean questions (does instantiation affect evaluation order? do generic calls introduce new choice sites? — expected answer no, but it must be argued) are not FG questions.
- **Dynamic semantics of full-language dispatch** (method sets, promotion, nil) — omitted per §1.2.

### 2.1 The guarantees it actually states, by anchor

**The formal core — `mem#model`:**
- A memory operation is (kind, program location, memory location, values); read-like vs write-like classified per primitive (mutex lock and channel receive are read-like; unlock, send, **close** are write-like).
- **Requirement 1**: per-goroutine operations form a correct sequential execution consistent with *sequenced before* — which is **defined by delegation to the spec**: "the partial order requirements set out by the Go language specification for Go's control flow constructs as well as the order of evaluation for expressions" (the file literally links `spec#Order_of_evaluation`). Consequence for us: our E-series latitude (E2–E5's unspecified evaluation orders) propagates verbatim into the memory model's Requirement 1 — sequenced-before is a *partial* order exactly where the spec leaves order open.
- **Requirement 2**: W restricted to synchronizing operations must be explainable by an implicit **total order** of synchronizing operations (SC for synchronization).
- *Synchronized before* = the observed subset of that total order; **happens before = transitive closure of (sequenced before ∪ synchronized before)**.
- **Requirement 3**: a non-synchronizing read must read a *visible* write (w happens-before r, and no intervening w′).
- Read-write and write-write **data race definitions** (unordered by happens-before, at least one side non-synchronizing).
- **DRF-SC**, stated as a provable property: race-free programs "can only have outcomes explained by some sequentially consistent interleaving of the goroutine executions", proof "the same as Section 7 of Boehm and Adve's paper" (PLDI 2008 — the model explicitly follows Boehm–Adve).

**The racy-program stance — `mem#overview` and `mem#restrictions`:**
- `mem#overview`: the data-race definition; DRF-SC informally ("behave as if all the goroutines were multiplexed onto a single processor"); the **refusal license**: "An implementation may always react to a data race by reporting the race and terminating the program"; and the **limited-outcomes stance**: otherwise each read of word-sized-or-smaller locations "must observe a value actually written to that location … and not yet overwritten" — "more like Java or JavaScript, in that most races have a limited number of outcomes, and less like C and C++, where the meaning of any program with a race is entirely undefined."
- `mem#restrictions` (the section is explicitly *informal*: "This section informally describes the semantics that implementations must provide for programs that do contain races"): report-and-halt is what `-race`/TSan does; a read/write of an **array, struct, or complex number may be implemented as per-sub-value accesses in any order**; word-sized reads must observe a preceding-or-concurrent write; "observation of acausal and 'out of thin air' writes is disallowed"; multiword accesses may tear, and races on (pointer,len)/(pointer,type) pairs "can in turn lead to arbitrary memory corruption" — the one place the limited-outcomes stance itself is bounded.

**The happens-before edge catalogue — `mem#synchronization` and children (each rule is a styled `p.rule`):**
- `mem#init`: if p imports q, completion of q's `init` functions happens before start of any of p's; completion of **all** `init` functions is synchronized before the start of `main.main`.
- `mem#go`: the `go` statement is synchronized before the start of the goroutine's execution.
- `mem#goexit`: a **non-edge, stated explicitly** — "The exit of a goroutine is not guaranteed to be synchronized before any event in the program"; the text even licenses "an aggressive compiler might delete the entire go statement" for an unobserved goroutine.
- `mem#chan`, four rules: (1) a send is synchronized before the **completion of** the corresponding receive; (2) the **close** of a channel is synchronized before a receive that returns zero-because-closed; (3) a receive from an **unbuffered** channel is synchronized before the completion of the corresponding send; (4) the *k*th receive on a channel with capacity *C* is synchronized before the completion of the *k+C*th send (the counting-semaphore generalization).
- `mem#locks`: for n < m, call *n* of `l.Unlock()` is synchronized before call *m* of `l.Lock()` **returns**; the RLock/RUnlock rule (there is an *n* such that Unlock *n* sync-before RLock's return, and RUnlock sync-before Lock *n+1*'s return); and TryLock's **explicit latitude grant**: an unsuccessful `TryLock` "has no synchronizing effect at all" and "may be considered to be able to return false even when the mutex l is unlocked" — spec-granted spurious failure.
- `mem#once`: completion of the single `f()` from `once.Do(f)` is synchronized before the return of **any** `once.Do(f)`.
- `mem#atomic`: if atomic operation A is observed by atomic operation B, A is synchronized before B; "All the atomic operations executed in a program behave as though executed in some sequentially consistent order"; "the same semantics as C++'s sequentially consistent atomics and Java's volatile variables". (This is U-6's forcing text.)
- `mem#finalizer`: `SetFinalizer(x, f)` is synchronized before the finalization call `f(x)`.
- `mem#more`: the delegation rule — sync's other types (Cond, Map, Pool, **WaitGroup**) and third-party packages document their own guarantees. This anchor is the charter for our DOCS evidence class: WaitGroup/Cond happens-before claims cite package docs *because the memory model says to*.

**Worked non-guarantees — `mem#badsync`:** double-checked locking and busy-wait loops shown broken; for the spinner: "there is no guarantee that the write to done will ever be observed by main … **The loop in main is not guaranteed to finish**."

**Compiler restrictions — `mem#badcompiler`:** the model "restricts compiler optimizations as much as it does Go programs": no invented writes (no conditional-inversion), no assuming loops terminate or calls return when hoisting accesses, no single read observing multiple values (no reload of a spilled local from shared memory), no single write writing multiple values (no using the target as scratch), with the recorded escape hatch: the prohibition on introducing races "does not apply if the compiler can prove that the races do not affect correct execution on the target platform" (valid at machine level, "would not be valid in a source-to-source translator" — directly relevant to how wide a *portable* semantics must be: the license is per-target, so the portable envelope cannot assume it).

## 3. Cox's gomm series — the rationale layer (web-sourced)

The series (research.swtch.com: hwmm → plmm → gomm; gomm is the 2021 design doc that became the 2022 revision) adds, beyond the normative text:

- **The deliberate middle position.** Go rejects both C++'s racy-UB ("the compiler may do anything at all") and Java's fully-defined racy semantics; races are invalid-but-bounded: report-and-terminate, else limited outcomes. This is a *designed constraint on implementations*, not an accident — the upper-bound reading is that a conforming implementation's racy behavior is genuinely bounded (word-sized reads see real values; no out-of-thin-air), which is why C10's refusal is a modeling choice, not a forced one. [web-sourced]
- **Why seqcst atomics, not acquire/release**: multi-location reasoning ("will just fail mysteriously" under acquire/release — WaitGroup and semaphore patterns given as witnesses) and the hardware trend (ARMv8 ldar/stlr); crucially, "using acquire/release atomics to make a program data-race-free does not result in a program that behaves in a sequentially consistent manner … such programs do not provide DRF-SC." Consequence for U-6: the seqcst pin at `mem#atomic` is a considered design commitment with recorded rationale, not a simplification we might find relaxed later — a conforming implementation may NOT weaken sync/atomic to acquire/release. [web-sourced]
- **The compiler-restrictions catalogue originates here** — the `mem#badcompiler` examples were proposed in gomm and are now normative. For the portable-semantics frame this is the sharpest upper-bound material in the whole lane: it enumerates transformations a conforming implementation must *not* perform, i.e., behaviors that are definitively outside the envelope. [web-sourced]
- **plmm's negative result frames C10 as state-of-the-art-aligned**: the out-of-thin-air problem is unsolved everywhere ("Prohibiting such causality violations in a way that does not also prohibit other desired optimizations turned out to be surprisingly difficult"); Java's and C++'s attempts at formal racy semantics failed; JS found DRF-SC bugs in its own model. No language has a satisfactory formal semantics for racy programs — so our doctrine position (racy programs refused fail-closed; "racy semantics is undefined by Go and unmodelable as a testable artifact today", register #4) is not a shortcut but the honest reflection of an open research problem. One nuance plmm/gomm sharpen: Go's racy semantics is *less* undefined than C's, so a future golean claim about bounded racy outcomes is not incoherent — merely far beyond current scope. [web-sourced]

**Fava/Steffen/Stolz** (JLAMP 103, 2019, doi 10.1016/j.jlamp.2018.10.004; FM 2018 conference version; searched, not read): an **operational** weak memory model for a Go-inspired calculus with **buffered channel communication as the sole synchronization primitive**, proving SC-DRF "using a standard simulation technique" — explicitly contrasted with axiomatic event-graph styles — plus an executable K-framework mechanization. Two hooks for us: (a) their theorem is the thing register #4 *assumes* (DRF ⇒ SC), proved for a channel-synchronized calculus — prior art for the NPDRF obligation (register #5); (b) their operational/simulation/executable methodology is our house style, so their proof structure is plausibly portable to our machine where an axiomatic proof would not be. [web-sourced, abstract-level only]

## 4. Verdicts

### 4.1 For mechanism 4.3 (divergence ledger) — entries this reading yields

1. **FG-dispatch-vs-gc-dispatch.** Sources: FG paper §3.4 Fig. 14 (`r-call` = call-time lookup) + its own §2.1 efficient-implementation prose (cite corrected by audit); Sulzmann/Wehr APLAS'21 §1 (the "different dynamic semantics" claim) and Theorem 1 + the 2022 extension (equivalence incl. divergence and panics, FG fragment only). Content: FG resolves methods at call time from the receiver's dynamic type; gc fixes the dictionary at interface-construction time. Stance: **proven observationally equivalent on the FG fragment; open beyond it** (method sets/pointer receivers, embedding, nil interfaces are outside the theorem). Bound affected: neither, today — GoCore's `TypeId`-keyed dispatch is FG-shaped and the differential pins it; the entry goes live at any generics/dispatch-representation arc. **Kind: none of the current enum fits** (`spec-ambiguity`/`spec-bug`/`gc-bug`/`gc-divergence-tolerated`/`ours` all presume spec-vs-gc-vs-us); this is model-vs-implementation prior art. Recommend 4.3 either adds a `prior-art` kind or records this as an informational entry — decide when the ledger lands.
2. **FGG-vs-shipped-generics.** FGG formalizes the 2019 draft design; shipped Go 1.18+ generics differ in surface (type sets, unions, `~`, constraint inference — none in FGG) and, per the FG paper's own prediction, in implementation strategy (a monomorphisation/runtime-representation mix). Stance: at the generics arc, FGG supplies typing skeleton + monomorphisability theory + the bisimulation obligation; the pinned spec supplies the language. Kind: informational/prior-art, same enum question as entry 1.
3. **Sequenced-before delegates to the spec** (`mem#model` Requirement 1 links `spec#Order_of_evaluation`): the memory model's per-goroutine order is a *partial* order exactly where the spec's evaluation order is open, so E2–E5's latitude is memory-model latitude too — under concurrency, unordered evaluation steps of one goroutine are additionally unordered against other goroutines' observations. Note-class entry; matters the day any E-series envelope interacts with a concurrent observer.
4. **Select has no memory-model text** — an absence record so C6/C7 auditors stop looking (their normative basis is spec-only).

### 4.3 For P5's memory-model deep-dive — recommendation: NO-GO on a weak-memory modeling arc; GO on two cheap targeted slices

**No-go on the big version** (a Fava-style weak/operational memory model inside GoCore): the machine's claim shape is SC-within-DRF with fail-closed refusal outside (register #4, C10), and the memory model's own DRF-SC guarantee (`mem#model`) makes SC interleaving *sound* for every program we accept — a weak memory semantics would add enormous cost to model behaviors we deliberately refuse to accept programs exhibiting. Even the atomics future (U-6) doesn't force it: `mem#atomic` pins atomics to seqcst, so atomics land as more SC synchronization, not as weak memory. The state of the art (plmm) says racy formal semantics is unsolved everywhere; there is no credible payoff at our current claim surface.

**Go on two slices that this reading makes concrete and cheap:**
- **The `mem#` retrofit of §2.2** — it is the P2 anchor retrofit for the concurrency section, and per the campaign's own framing the retrofit *is* a fidelity re-read of every envelope argument. The §2.2 list is the worklist.
- **Detector-HB-vs-`mem#model` correspondence review**: C10's edge set is deliberately TSan-targeted, with deviations quoted at implementation sites (U1–U5, register #13). A one-time review reading each detector edge against the formal HB definition (Requirements 1–3 + the `mem#synchronization` catalogue) — including the close-edge direction (rule 2), the buffered-channel counting rule (rule 4), and the goexit non-edge — would either confirm register #13's scope ledger or find the next BUG-045-class item. Small, bounded, high-value.
- Read Fava et al. in full **only when register #5 (NPDRF) reaches its proof stage** — as proof-technique prior art (operational simulation, executable), not as a modeling target. Acquire the PDF into `deps/papers/` with a manifest row at that point (or opportunistically at the next P0 touch).
