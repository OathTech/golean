# Dossier E7 — hidden-dependency initialization order (pinned to go/types' conforming order, known ≠ gc)

G3 register item 5. Inventory §E7; init design
`docs/2026-08-05_init-design.md` §1. Proposal only — batched for user
ruling.

## 1. The latitude

Package-level variable initialization order is spec-determined
(stepwise, earliest-ready) EXCEPT where a variable's initializer
reaches another variable through a channel the per-package lexical
dependency analysis cannot see (canonically: a method called through
an interface conversion). There the order is unspecified. The
frontend realizes go/types' `InitOrder` (one conforming order); gc's
own initorder analysis is coarser and realizes ANOTHER conforming
order on exactly the spec's example shape.

## 2. Evidence

### SPEC (go1.26.5, §Package initialization)

> "Dependency analysis is performed per package; only references
> referring to variables, functions, and (non-interface) methods
> declared in the current package are considered. If other, hidden,
> data dependencies exists between variables, the initialization order
> between those variables is unspecified."

And of its own example (`var x = I(T{}).ab()` ...):

> "the variable a will be initialized after b but whether x is
> initialized before b, between b and a, or after a ... is not
> specified."

Note the spec names THREE legal positions for x — the plausible
envelope is all linear extensions of the lexical-reference partial
order with hidden-dep-affected variables freed (the inventory's
statement).

### GC probe (`docs/evidence/2026-08-15-dossier-e7/`, verbatim)

The spec's example shape, readout-instrumented:

    4624242

gc initializes hiddenX AFTER hiddenA/hiddenB. go/types' InitOrder —
the frontend's realization — puts hiddenX FIRST (readout 4242). Both
conforming. This is the recorded standing differential red
(`init/hidden-dep-order`), the realized order mechanically pinned by a
deviation-observation pin (check-golden then; scripts/check-frontend-pins
since the 2026-08-31 repo split) so drift to a THIRD order is
caught.

### The distinguishing severity facts (why this outranks its E-cluster peers)

1. It is the doctrine's TOO-NARROW, soundness-relevant direction on
   the SEQUENTIAL side: theorems proved over our order do NOT transfer
   to gc executions of hidden-dep programs — not a panic-identity
   nicety but wrong VALUES (4242 vs 4624242).
2. The deferral is UNGUARDED: no frontend check detects the
   hidden-dep shape, so an affected program is silently translated
   with a possibly-gc-divergent init order. Every other known-≠-gc
   sequential pin (E3/E4/E5) is either shape-refused (E6) or confined
   to panic identity; this one can change ordinary program output.
3. North-star exposure is real: etcd-io/raft has package-level vars —
   the inventory records "must be checked at the target lane".

### Corpus / de-facto spec

Deployed code DOES depend on init order broadly (the ordered,
analysis-visible part — idiomatic Go relies on it constantly), but
hidden-dep shapes specifically are rare and known-sharp: the Go team
documented the latitude with a worked example precisely because real
code hit it (the spec example's `sideEffect()` framing; assertion
about motivation is local knowledge, UNVERIFIED). gc and go/types
disagreeing on the SPEC'S OWN EXAMPLE is strong evidence the latitude
is real and exercised, not theoretical.

### XIMPL / ARCH

XIMPL partially in hand, uniquely for this register: go/types and gc's
compiler are two INDEPENDENT analyses realizing different conforming
points (both from the same project, but independently implemented —
the divergence is the datum). gccgo NOT-OBTAINED. ARCH: the
hidden-dependency sentence has been in the spec since Go 1 era
(local knowledge, UNVERIFIED); no proposal to close it known.

## 3. Proposed disposition

**INTERIM FAIL-CLOSED FRONTEND DETECTOR NOW; full conforming-orders
envelope DEFERRED** (= inventory §7 item 3, affirmed with evidence).

- THE PROPOSAL: (i) a frontend detector for the hidden-dep shape —
  method-value/method-expression reachability through interface
  conversion out of any package-level initializer — that REFUSES the
  package (visible red, "hidden init dependency: order unspecified"),
  converting the unguarded silent-divergence class into a refusal;
  (ii) the full envelope (a named Choices site over conforming
  orders) stays deferred with its recorded MODERATE cost ($pkginit
  becomes schedule-bearing; strict-lane init cases stay on the
  deterministic default point).
- ARGUMENT: the detector is LOW cost, closes the only UNGUARDED
  soundness-direction hole in the sequential register, and preserves
  every existing green init case (hidden-dep-free programs are
  spec-FORCED to one order — §4 of the inventory — and unaffected).
  Fail-closed is the project's default for exactly this situation.
- COUNTER-ARGUMENT (do the full envelope instead): a refusal is
  coverage debt; the envelope is the honest end state and the detector
  might reduce pressure to build it. REBUTTAL: the envelope's cost is
  real and its value today is one corpus case; the detector's refusal
  KEEPS the debt visible (a red is pressure) while removing the
  silent-wrong-answer window; the ruling can queue both.
- COUNTER-ARGUMENT (do nothing — the deviation record + golden pin
  already catch drift): the pin only guards the ONE corpus case; any
  user/target program with the shape gets silence. REBUTTAL: that is
  the definition of fail-open; the project's contract ("fail closed,
  always") decides this.
- WHAT WOULD CHANGE THE ANSWER: (i) the raft target-lane check coming
  back positive (hidden-dep shape present in the north star) — then
  the FULL envelope jumps the queue, because refusing the north star
  is not acceptable for long; (ii) the detector's
  reachability analysis proving as expensive as the envelope itself
  (unlikely — go/types exposes the needed selections).
