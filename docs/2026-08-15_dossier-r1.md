# Dossier R1 — `int`/`uint` width (pinned to 64 bits)

G3 register item 10. Inventory §R1 (also register extension #6; §9
flag 2 records the missing site-level caveat). Proposal only —
batched for user ruling.

## 1. The latitude

`int`, `uint` (and `uintptr`) are implementation-sized. The machine
pins 64 (`IntKind.bits?`, Value.lean:33–34; `IntKind.normalize` wraps
at the fixed width); the frontend maps `uintptr` to uint64
(observations of it refused); the negative lane inherits the pin via
go/types on the host.

## 2. Evidence

### SPEC (go1.26.5, §Numeric types)

> "There is also a set of predeclared integer types with
> implementation-specific sizes:
> uint     either 32 or 64 bits
> int      same size as uint
> uintptr  an unsigned integer large enough to store the uninterpreted
> bits of a pointer value"

The envelope is exactly {32, 64} — the spec's own enumeration; wider
or narrower is non-conforming.

### GC probes (`docs/evidence/2026-08-15-dossier-r1/`, verbatim)

- Native: `strconv.IntSize: 64`, `unsafe.Sizeof(int(0)): 8`, 64 bits
  in `^uint(0)` — the oracle host realizes 64.
- ACCEPTANCE, both points: `const big int = 1 << 62` runs on amd64;
  under GOARCH=386 the SAME toolchain REJECTS it: `cannot use 1 << 62
  (untyped int constant 4611686018427387904) as int value in constant
  declaration (overflows)`. The other width point is REAL and
  realized by gc itself — not hypothetical — and it bites first in
  the negative lane (which programs compile at all).
- 32-bit RUNTIME datum: NOT-OBTAINED — the 386 binary cross-compiles
  but this host cannot execute it (exit 133; recorded in output.txt).

### Corpus / de-facto spec

Deployed Go increasingly assumes 64-bit int (len of large slices,
time math, hash mixing) — but the ecosystem still BUILDS for 32-bit
targets (GOARCH=386/arm/wasm's wasm32-adjacent modes; TinyGo's
microcontrollers), so the de-facto spec keeps both points alive.
Code that must care uses `strconv.IntSize`/`math.MaxInt` — the
standard library itself is width-portable by policy (local knowledge,
UNVERIFIED for a citable policy text).

### XIMPL

Partially OBTAINED, unusually: GOARCH=386 IS a second width
realization by the same implementation (acceptance datum committed).
TinyGo realizes 32-bit int on AVR/ARM targets (documentation
citation from local knowledge, UNVERIFIED). A runnable 32-bit lane
remains the missing piece.

## 3. Proposed disposition

**KEEP THE 64-BIT PIN; ADD the owed site-level caveat at
Value.lean:33 (a semantic-core-lane task — §9 flag 2 already owes
it); parameterize only when a 32-bit oracle lane exists.**

- ARGUMENT: the pin matches the only runnable oracle; the re-envelope
  is PERVASIVE-but-mechanical (IntKind.bits?, normalize, conversions,
  frontend Sizes config, negative-lane acceptance) and worthless
  without an oracle to differentiate the other point — the
  differential would validate nothing. The probe sheet shows the
  32-bit ACCEPTANCE half is cheap when wanted (GOARCH=386 go/types
  Sizes on the host — no new toolchain), so the negative-lane half of
  the re-envelope could land independently and early if the user
  wants acceptance-portability claims.
- COUNTER-ARGUMENT: 32-bit targets are real (386/arm/tinygo) and the
  width leaks into ACCEPTANCE, so theorems + the negative lane are
  silently amd64-scoped today with no site-level record. REBUTTAL:
  true, and that is why the caveat (the already-owed §9 flag 2 fix)
  should land NOW even though the parameterization waits — the
  honesty gap and the machinery gap are separable; this dossier
  proposes closing the first immediately.
- WHAT WOULD CHANGE THE ANSWER: a 32-bit execution environment
  (qemu-user, a 386-capable host, or TinyGo) making a second
  differential lane runnable; or a target program whose correctness
  argument depends on width portability.

## 4. Evidence gaps

- 32-bit RUNTIME observations: NOT-OBTAINED (host cannot execute 386
  binaries; no emulator installed — installing one is outside this
  lane's rules). What would obtain: qemu-i386 or any 32-bit runner.
- TinyGo width documentation: cited from local knowledge, UNVERIFIED
  (no web).
