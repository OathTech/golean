# Dossier R8 — WaitGroup counter representation (pinned to gc's bit layout)

G3 register item 14. Inventory §R8 (register extension #7's family);
BUG-055. Borderline-IN scoping judgment (g3.md): sync-package item,
but the latitude is representational arithmetic observable from a
single goroutine. Proposal only — batched for user ruling.

## 1. The latitude

The sync docs say only that Add "panics if the counter goes negative"
— nothing about counter width or wrap. gc keeps the counter in the
high 32 bits of a uint64 and WRAPS before the negative test
(waitgroup.go:104/109). Machine: the BUG-055 formula at the `wgAdd`
arm — `counter' = ((counter + delta + 2^31) emod 2^32) − 2^31`.
Plausible envelope: any counter semantics consistent with the doc
sentence (unbounded, 32-bit wrap, 64-bit wrap, saturation...).

## 2. Evidence

### DOCS (sync package; the governing text)

> "Add adds delta, which may be negative, to the WaitGroup task
> counter. ... If the counter goes negative, Add panics."

(Quoted from the pinned toolchain's package documentation; the
sentence underdetermines everything at ≥ 2^31 scale.)

### GC probes (`docs/evidence/2026-08-15-dossier-r8/`, verbatim)

- `Add(-1)` at zero: `sync: negative WaitGroup counter` — as a PLAIN
  STRING panic value (`recovered (string? true)`), witnessing the
  BUG-054 box-class distinction alongside.
- `Add(1<<31)` (a POSITIVE delta): panics `negative WaitGroup
  counter` — the wrap-before-test realization; an unbounded-counter
  implementation would accept it.
- `Add(2^31-1)` ok, then `Add(1)`: panics — the wrap boundary is
  exactly 2^31, matching the machine's formula bit-for-bit.

Pre-fix the machine diverged in BOTH directions here (BUG-055's
record); the probes confirm the fixed arm sits on gc's realized
point.

### Corpus / de-facto spec

Real WaitGroup usage lives in |delta| ∈ {1, small}; a counter
anywhere near 2^31 is unreachable without deliberate misuse (2^31
goroutines is not a real program). The doc text underdetermines
behavior ONLY at misuse scale — deployed code exerts no pressure on
the wrap semantics at all.

### XIMPL / ARCH

NOT-OBTAINED. gccgo uses the same runtime/sema layout in modern
versions (local knowledge, UNVERIFIED). ARCH: the 32/32 bit packing
is a gc implementation detail that has changed shape across releases
(state layout, not semantics; local knowledge, UNVERIFIED).

## 3. Proposed disposition

**PERMANENT-PIN at gc's realized layout, version-tracked** — the
inventory's candidate posture, affirmed with the wrap boundary now
probed on both sides.

- ARGUMENT: the divergence surface exists only at misuse-scale
  deltas; every observation there is a panic-vs-no-panic on a
  program no deployed code resembles. An envelope over counter
  semantics would carry a Choices-free but multi-outcome arm for
  zero verification value. The pin is already differentially
  version-tracked (BUG-055's cases fire on toolchain movement).
- COUNTER-ARGUMENT: the modeled machine should not encode gc's
  internal bit packing — it is the definition of over-fitting to one
  implementation. REBUTTAL: the alternative is refusing ≥ 2^31
  deltas (fail-closed) — defensible, but it converts a
  correctly-modeled total function into a refusal for no consumer's
  benefit; the pin with its recorded envelope note is strictly more
  useful and equally honest.
- WHAT WOULD CHANGE THE ANSWER: XIMPL evidence of a different
  realization (e.g. a 64-bit counter in another implementation —
  would motivate the refusal posture over a two-point envelope,
  since no program anyone verifies distinguishes them); a doc change
  specifying the counter's range.
