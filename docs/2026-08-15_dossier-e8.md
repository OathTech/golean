# Dossier E8 — multi-file declaration order (narrowed to sorted-by-filename)

G3 register item 6. Inventory §E8; init design
`docs/2026-08-05_init-design.md` §1.2. Proposal only — batched for
user ruling.

## 1. The latitude

The declaration order of package-level variables across multiple files
— which feeds initialization order — is "the order in which the files
are presented to the compiler". The frontend sorts files by name
(tools/nativefrontend, sort.Strings), pinned by the corpus case
`init/multi-file-order`.

## 2. Evidence

### SPEC (go1.26.5, §Package initialization)

> "The declaration order of variables declared in multiple files is
> determined by the order in which the files are presented to the
> compiler: Variables declared in the first file are declared before
> any of the variables declared in the second file, and so on. To
> ensure reproducible initialization behavior, build systems are
> encouraged to present multiple files belonging to the same package
> in lexical file name order to a compiler."

"Encouraged", not required — any presentation order conforms.

### GC probes (`docs/evidence/2026-08-15-dossier-e8/`, verbatim)

Two dependency-free recorder vars in `za.go`/`zb.go`:

- package (directory) mode: `ab` — the go command sorts by file name.
- explicit sorted file list: `ab`.
- explicit REVERSED file list (`go run zb.go za.go main.go`): `ba`.

NEW DATUM beyond the inventory's entry: the other member of the
envelope is reachable with the STANDARD toolchain — an explicit
file-argument list presents files in argument order; no conforming
non-go-command build system is needed to realize it. The inventory's
"a conforming NON-go-command build system could present files in any
order" understates: `go run`/`go build` with file args IS such a
presenter.

### Corpus / de-facto spec

Overwhelmingly, deployed Go is built in package mode (go build/test of
packages, modules) — sorted order. Explicit multi-file `go run`
invocations are a scripting corner (and even then usually sorted
because humans list files alphabetically). De-facto pressure pins the
sorted point for real projects; the spec's "encouraged" sentence
exists precisely to bless that convergence. The frontend consumes a
DIRECTORY (`--dir`) and sorts — it structurally cannot receive an
unsorted presentation today, so within the tool's own input space the
narrowing is not even reachable from outside.

### XIMPL / ARCH

gccgo accepts file lists on its command line and presents them in
argument order (compiler-driver behavior; local knowledge,
UNVERIFIED). ARCH: the "encouraged" sentence was added to bless
go-command behavior (local knowledge, UNVERIFIED). NOT-OBTAINED
otherwise.

## 3. Proposed disposition

**PERMANENT-RECORD NARROWING with a sharpened transfer scope:
"directory/package-mode builds and sorted file lists" (not "the go
command"). Revisit trigger: a target built from an unsorted explicit
file list — or any non-go-command build system.**

- ARGUMENT: the frontend's input space is a directory; the sorted
  order is forced there, matches package-mode gc exactly, and every
  realistic target (modules, the north star) is package-mode. Widening
  to an order envelope would make $pkginit schedule-bearing for zero
  reachable benefit — the inventory's "cost of widening near-zero
  benefit" judgment stands, now with the probe record behind it.
- COUNTER-ARGUMENT: the reversed-file-list probe shows the excluded
  member is one `go run` invocation away, so "no conforming presenter
  exists" is false and the narrowing is a genuine hole. REBUTTAL: the
  hole is unreachable THROUGH THE TOOL (directory input, sorted);
  the honest fix is the sharpened scope sentence this dossier
  proposes, not machinery. A theorem's transfer claim should say
  "as built by package-mode go" — that is a caveat, and caveats are
  the permanent-record disposition's currency.
- WHAT WOULD CHANGE THE ANSWER: a supported entry path that accepts
  explicit file lists (then the frontend must either sort-and-record
  — staying in the narrowing with a visible normalization — or refuse
  unsorted lists fail-closed; the ruling should pick the posture in
  advance: proposal = sort-and-record, since the normalization is
  observable and lossless).
