# Dossier E2 — call vs. assignment-target operands (pinned: gc's call-first)

G3 register item 1 (`docs/gallery-campaign-log/g3.md`). Inventory:
`docs/2026-08-11_latitude-inventory.md` §E2. Proposal only — no
machine, corpus, or baseline change; batched for user ruling.

## 1. The latitude

For `lhs..., x = f(...)` (a multi-target assignment whose RHS is a
call), the relative order of (i) the call's evaluation and (ii) the
evaluation of the targets' operands (index operands, a deref target's
pointer, an index target's slice-header base) is spec-unspecified. A
callee that mutates a target operand makes the choice observable in
both panic directions and in stored values.

## 2. Evidence

### SPEC (go1.26.5 `$GOROOT/doc/go_spec.html`, §Order of evaluation)

> "Otherwise, when evaluating the operands of an expression,
> assignment, or return statement, all function calls, method calls,
> receive operations, and binary logical operations are evaluated in
> lexical left-to-right order."

and, of the spec's own example `y[f()], ok = g(z || h(), i()+x[j()],
<-c), k()`:

> "However, the order of those events compared to the evaluation and
> indexing of x and the evaluation of y and z is not specified, except
> as required lexically. For instance, g cannot be called before its
> arguments are evaluated."

The `lhs..., x = f(...)` class sits squarely in that carve-out on
GoCore's expression surface: the frontend hoists nested calls/receives
out of target operands (A-normal form), so by the time the rule fires
the left-hand operand reads are call- and receive-free — nothing the
"except as required lexically" qualifier orders remains among them
(the rule-site block, Machine.lean:2587–2626, quotes this verbatim).

### GC probes (lower bound — `docs/evidence/2026-08-15-dossier-e2/`)

Three discriminating directions, all realizing CALL-FIRST, verbatim:

- index-panic (callee sets the index operand out of range):
  `panic: runtime error: index out of range [5] with length 3` — the
  operand was read post-call.
- value-order (callee moves the operand 0→2): `10 11 42 7` — the store
  landed at `xs[2]`, not `xs[0]`.
- deref-target (callee repoints the target's pointer): `a 0 b 42 j 7`
  — the store went through the NEW pointee.

The record of authority beneath these confirmations: the BUG-052
S1-audit probe matrix (docs/BUGS.md, BUG-052 — missed/spurious index
panic, global index, deref target, slice-header base) with five
oracle-backed corpus pins (`multi-assign/call-write-back-order/*`) and
the `.callValue` discriminator twins, all VERIFIED RED at the pre-fix
machine — the pin is differentially guarded in both directions.

### Machine site (read-only citation)

Machine.lean:2587–2626, the PINNED LATITUDE block: call evaluates
first (arguments left-to-right, frame entry), caller-target plans ride
the frame untouched, target operands evaluate at frame EXIT through
the tgtOpK spine, then per-target `storeK` stores. The site consumes
NO Choices. Its SCOPE clause explicitly excludes the inter-target axis
(E3's dossier).

### Corpus / de-facto spec

Deployed Go code overwhelmingly does not write callees that mutate
their own assignment's target operands — the discriminating shape is
an anti-idiom (golint-era style guides warn against side-effecting
calls in multi-assignments precisely because the order is unspecified;
assertion from local knowledge, UNVERIFIED against a citable text).
De-facto pressure on this point is therefore WEAK: no large body of
code pins either order, which is also why gc has been free to keep its
compiler-internal realization.

### XIMPL / ARCH

NOT-OBTAINED. No second toolchain in this lane and no web access.
What would obtain it: run the three probes under gccgo and tinygo —
if either realizes operand-first, the two-point envelope stops being
hypothetical. ARCH note (local knowledge, UNVERIFIED): the Go team has
declined to specify assignment-operand order when asked (the long-open
spec-clarification issue on evaluation order); no proposal commits gc
to call-first.

## 3. Proposed disposition

**KEEP THE PIN (gc's call-first point), obligation recorded, queue
position unchanged.**

- ARGUMENT: the pin sits at gc's probed realization, is version-tracked
  by five differential pins that fire on toolchain movement, and the
  spec text is quoted verbatim at the rule site. The plausible envelope
  (both orders, plus interleavings of operand evaluation with the
  call's effects) has no witness in any known implementation for the
  non-gc points — XIMPL is the missing evidence class, and widening
  before it exists would be modeling behavior never observed anywhere,
  purchased at MODERATE-HIGH cost (the call/frame-exit arms, the wp
  call-law family restated a second time — the inventory's stated cost
  ceiling, stream-bound metadata, five pins converted to membership
  rows).
- COUNTER-ARGUMENT: the doctrine says the machine should be the
  WEAKEST machine Go can plausibly do, and the spec plainly permits
  operand-first; a conforming implementation choosing it would make
  every theorem over call-bearing multi-assignments non-transferable.
  The two-bounds doctrine does not require observed members to widen —
  the upper bound is argued from spec text, which here clearly admits
  the second point.
- WHY KEEP ANYWAY (the judgment): the divergence is sequentially
  observable ONLY in the callee-mutates-target-operand anti-idiom;
  theorems over programs free of that shape transfer under either
  realization. The honest cost of the pin is a standing transfer
  caveat scoped to that shape, which is narrow and detectable. §7 of
  the inventory ranks the E-cluster's open axes (E3/E4/E5) above this
  pin precisely because THERE the oracle already sits outside our
  point; here it sits on it.
- WHAT WOULD CHANGE THE ANSWER: (i) any conforming implementation
  observed realizing operand-first (XIMPL datum); (ii) a gc release
  moving the realization (the five pins go red — the site text already
  commits to revisiting the pin, not the spec claim); (iii) a target
  program in the import lane that actually contains the discriminating
  shape.
