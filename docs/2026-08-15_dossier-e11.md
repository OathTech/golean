# Dossier E11 — runtime check order inside one operation (pinned to gc)

G3 register item 9. Inventory §E11. Proposal only — batched for user
ruling.

## 1. The latitude

The spec MANDATES the run-time panics (a violated slice bound, an
unhashable map key, a failed interface assertion) but says nothing
about the ORDER of the checks WITHIN one operation when several would
fire. Observable as which panic message appears. Machine: slice bounds
HIGH then LOW (`checkSliceBounds`/`checkSliceBounds3`,
Ops.lean:173–218); map-key hashability walk stops at the first
offending component in gc's hashing order (Ops.lean:1564–1611);
interface-assert panic names the first unmet method in name-sorted
order (Ops.lean:716–747).

## 2. Evidence

### SPEC (go1.26.5)

§Slice expressions: "if the operand is a slice, the upper index bound
is the slice capacity cap(a) rather than the length... If the indices
are out of range at run time, a run-time panic occurs." §Run-time
panics: "The exact error values that represent distinct run-time error
conditions are unspecified." Neither text orders multiple simultaneous
violations — the check order is pure implementation residue.

### GC probes (`docs/evidence/2026-08-15-dossier-e11/`, verbatim)

- `s[5:4]` (lo>hi AND hi>cap): `slice bounds out of range [:4] with
  capacity 3` — HIGH check first, the machine's order.
- `s[1:5:2]`: `slice bounds out of range [:5:2]` — the hi-vs-max
  violation rendered.
- Assertion missing Alpha and Gamma (declared order Gamma, Beta,
  Alpha): `missing method Alpha` — NAME-SORTED, not declaration
  order; the machine's order.
- Map key `[2]interface{}{func(){}, map[int]int{}}`: `hash of
  unhashable type func()` — first component in hashing order; the
  machine's walk.

All four realized orders coincide with the machine's pins.

### Corpus / de-facto spec

Programs dispatching on WHICH of two simultaneous bound violations is
reported would be dispatching on unspecified message content (R9's
caveat covers them). The check order matters to the equality lane
only because message identity is already pinned — which is exactly
the inventory's point: "an order envelope without a message envelope
buys nothing". De-facto pressure: none.

### XIMPL / ARCH

NOT-OBTAINED. gccgo's messages differ textually (R9's note), so its
check order would be evidence for the ENVELOPE's width but useless to
the equality lane. ARCH: none known.

## 3. Proposed disposition

**PERMANENT-PIN alongside R9, now probe-backed.** The check order and
the message identity are one observable; R9 pins the messages, so the
order rides that pin and shares its caveat (no message-content claim
transfers beyond gc).

- ARGUMENT: the inventory's own analysis, confirmed by four probes at
  the machine's exact orders. An order envelope would multiply
  admitted messages for zero verification value while the oracle is
  gc.
- COUNTER-ARGUMENT: a conforming implementation with the other check
  order makes strict-lane panic-message claims non-transferable.
  REBUTTAL: already true via R9 (message TEXT is unspecified); the
  order adds no new exposure beyond R9's standing caveat.
- WHAT WOULD CHANGE THE ANSWER: R9 itself being re-ruled (an order
  envelope only makes sense inside a message envelope); or a
  cross-implementation equality lane.

## 4. Evidence gaps

- XIMPL: NOT-OBTAINED (probes ready).
- The two-index slice probe conflates lo>hi with lo>cap shapes;
  a fuller matrix (each violation pair isolated) was skipped per the
  divergence guard — the probed pairs suffice to witness gc's
  high-then-low and hi-vs-max realized orders.
