# Dossier E3 — inter-target phase-1 operand order (pinned to OUR point, known ≠ gc)

G3 register item 2. Inventory §E3; BUG-032 round-4/S1-delta
amendments (docs/BUGS.md). Proposal only — batched for user ruling.

## 1. The latitude

In a multi-target assignment, which TARGET's operands evaluate first
(target-vs-target) is spec-open: §Order of evaluation orders only
calls, receives, and binary logical operations. When two or more
targets' operand evaluations panic, the choice selects WHICH panic the
program reports. The machine walks targets left-to-right (the tgtOpK
spine); gc realizes a compiler-internal order.

## 2. Evidence

### SPEC (go1.26.5, §Order of evaluation)

> "Otherwise, when evaluating the operands of an expression,
> assignment, or return statement, all function calls, method calls,
> receive operations, and binary logical operations are evaluated in
> lexical left-to-right order."

Nothing else about operand order is specified — target-vs-target
operand order is exactly the residue ("the order of those events
compared to the evaluation and indexing of x ... is not specified").
Both realizations conform.

### GC probes (`docs/evidence/2026-08-15-dossier-e3/`, verbatim)

- `aa[5][0], b[*pn] = f6()` → gc reports the SECOND target's panic
  (`invalid memory address or nil pointer dereference`); the machine's
  left-to-right point reports the first (`[5] with length 3`).
- Targets swapped → gc's answer FLIPS (`index out of range [5] with
  length 3`) — ordering, not panic-kind priority.
- Three panicking targets → gc picks the MIDDLE (`[9] with length 3`);
  identical under `-gcflags=all="-N -l"` (output-noopt.txt) — the
  realization is compiler-internal and NOT an optimizer artifact,
  hence UNPINNABLE (a pin would chase an implementation detail gc
  itself does not document and could permute per shape/version).
- The call-free assignMany twin realizes the same second-target pick —
  the axis is independent of E2's call pin.

These reproduce the BUG-032 S1-delta record exactly (reviewer probes
`.tmp/probe052/case12,13` genres, verifier-reproduced there;
re-exhibited first-hand here).

### Containment fact (recorded, code-verified at the record)

The divergence CANNOT escape panic selection into side effects: the
frontend hoists calls out of target operands (probed at the BUG-032
record), so target operands are call-free and their evaluation is
effect-free — the only observable difference is which panic value the
program dies/recovers with. E6 (the len/cap hoist refusal) exists
because realizing gc's point for receive-bearing shapes would need
full-statement linearization — deliberately not built; the refusal
keeps that shape visible instead of silently misordered.

### Corpus / de-facto spec

Programs whose correctness depends on WHICH of two simultaneous
operand panics is reported are essentially nonexistent in deployed
code (a program recovering and dispatching on the panic message of a
multi-panic assignment is already outside gc's own compatibility
surface — panic message text is unspecified, R9). De-facto pressure:
NONE measurable. This is the doctrine's cleanest case of latitude that
deployed code does not pin.

### XIMPL / ARCH

NOT-OBTAINED (no second toolchain, no web). gccgo running the probe
matrix would give a third realized point; ARCH note (local knowledge,
UNVERIFIED): no Go proposal has sought to specify assignment operand
order.

## 3. Proposed disposition

**PANIC-IDENTITY MEMBERSHIP ENVELOPE — admit any candidate target's
panic; do NOT linearize.**

- THE PROPOSAL: classify the discriminating shapes (≥ 2 potentially
  panicking target operand sets in one assignment) under a membership
  envelope whose admitted observation set is {each candidate target's
  operand panic}, machine's left-to-right point kept as the canonical
  deterministic realization. This is the inventory's own sketched
  option ("panic-identity membership envelope — needs status-diverse
  membership machinery pointed at panic identity") and §7 item 5's
  queue entry.
- ARGUMENT: gc is KNOWN outside our point (probed, stable), so under
  the doctrine's bug definition this is an observed-∉-modeled
  candidate on the strict lane — the too-narrow, soundness-relevant
  direction. A membership envelope makes the standing differential
  divergence honest (gc's member admitted) without building
  full-statement linearization, which BUG-032 records as deliberately
  rejected (cost + it would only chase an unpinnable internal order).
  The envelope's width is argued from spec text (any target order
  conforms), not from gc sampling.
- COUNTER-ARGUMENT (for linearization instead): an envelope over panic
  identity weakens strict-lane claims on these shapes from equality to
  membership; a full linearization with an order Choices site would
  keep per-stream determinism and let the enumerator quantify it.
  REBUTTAL: the observable surface is panic identity only (containment
  fact above), so the envelope loses nothing a theorem consumer can
  see, at a fraction of the cost; BUG-032 already records why
  linearization was rejected.
- COUNTER-ARGUMENT (for keeping the bare pin): the shape is anti-idiom
  and rare; the standing deviation record + E6's refusal already keep
  it honest. REBUTTAL: unlike E2, the oracle is KNOWN outside the
  modeled point today — the doctrine explicitly refuses to be "at
  peace with" that (§8 correction paragraph, adopted); a recorded red
  is a debt with a queue position.
- WHAT WOULD CHANGE THE ANSWER: (i) membership machinery proving
  harder to point at panic identity than linearization (cost
  inversion); (ii) a gc release documenting/stabilizing its order
  (would make a gc-point pin possible — though still only one member);
  (iii) XIMPL data showing all implementations realize some common
  restricted order (could narrow the argued width).

## 4. Evidence gaps

- XIMPL: NOT-OBTAINED; probe matrix ready for gccgo/tinygo.
- gc's internal order itself: UNPINNABLE by construction
  (compiler-internal, shape-dependent); no further probing can close
  it — this gap is permanent and is itself evidence FOR the envelope
  treatment.
